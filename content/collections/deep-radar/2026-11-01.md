## 01 · io_uring：`need_resched()` 只应让出 CPU，不应偷走剩余忙轮询预算

**原文与日期：** Pavel Begunkov，2026-10-28 04:48（中原标准时间）；[io_uring 邮件原帖](https://lore.kernel.org/io-uring/20261027204840.7823-1-notprairie@gmail.com/) 与 [LKML/Openwall 镜像及完整 diff](https://lists.openwall.net/linux-kernel/2026/10/27/2762)。

**为什么值得读：** 这是一个很小却很有迁移价值的状态机错误。io_uring 只注册一个 NAPI 时，把结束回调直接交给 `napi_busy_loop_rcu()`；内核看到 `need_resched()` 后退出内层循环，io_uring 却把这次“调度让步”误判成 10ms 忙轮询预算已经耗尽，随后进入睡眠。多 NAPI 路径有外层循环重新进入，反而不受同一问题影响。

**核心技术结论：** v2 在 `io_wait_queue` 中保存绝对截止时间 `napi_busy_poll_end`。内层 NAPI loop 因 `need_resched()` 返回后，io_uring 只要发现截止时间未到，就再次进入忙轮询；真正超预算、收到事件或等待条件改变时才结束。补丁保留 held-NAPI 快路与静态注册语义，没有把 `need_resched()` 屏蔽掉，因此仍允许调度器取得控制权。

```c
/* 关键不是延长 timeout，而是把“本次 inner loop 结束”
 * 与“整个 io_uring busy-poll 预算结束”分开。 */
while (!io_napi_busy_loop_should_end(iowq, start_time))
    napi_busy_loop_rcu(napi_id, loop_end, iowq, true, budget);
```

**最有价值的实验、源码与 benchmark 细节：** 测试基于 `io_uring-7.4`、x86-64、`HZ=1000`、PREEMPT_DYNAMIC lazy、未做 CPU isolation，r8169 仅 1 个 RX queue，busy-poll 预算 10ms。一个固定在 CPU 上的 `SCHED_FIFO` waker 每 1ms 唤醒一次：单 NAPI 在修复前每个 10ms 周期只忙轮询约 0.5–1.5ms，约 0.8M polls/s；修复后可用满约 10ms，约 16.2M polls/s，循环计数约 20.25 倍。无 waker 控制组为 15.3M → 16.2M；双 NAPI 控制组 7.2M → 7.1M，说明修复瞄准的是单 NAPI 的提前退出，而非泛化地提高轮询频率。作者用 bpftrace 同时跟踪 `__io_napi_busy_loop()` 进出、`napi:napi_poll` 和结束回调返回值。注意这些是 loop-rate 与 budget-consumption 数据，不等于应用吞吐；动态 NAPI 注册走同一路径但未单独实测，后续 `cond_resched()` 调整也明确留待另一补丁。

**适合的工程师背景：** 熟悉 io_uring、NAPI、busy polling、Linux 调度抢占点，或在网络 I/O 中维护“时间预算 + 可抢占内层循环”的工程师。

**预计阅读收益：** 约 35–50 分钟；能学会把局部循环退出原因与全局预算状态解耦，并用单 NAPI、双 NAPI、空闲和定时唤醒四组对照定位行为差异。

## 02 · Kotlin/Native：让 LLVM 在进程内直接发射目标文件

**原文与日期：** JetBrains Kotlin 团队，2026-10-30 21:41（中原标准时间）；[Kotlin PR #9434](https://github.com/JetBrains/kotlin/pull/9434)、[KT-90368 benchmark 与设计记录](https://youtrack.jetbrains.com/issue/KT-90368) 及 [33 个文件的源码 diff](https://github.com/JetBrains/kotlin/pull/9434/files)。

**为什么值得读：** Kotlin/Native 的 per-file incremental cache 在一个拥有数千源文件的工程中，会把 N 个 LLVM module 逐个序列化成 bitcode，再为每个文件启动一次外部 clang 生成 object；不仅写盘与读盘重复，clang 初始化也无法复用。补丁引入实验性 `-Xin-process-obj-emission`，直接把活的 `LLVMModuleRef` 交给 LLVM C API，是真正沿数据生命周期删除边界成本，而不是微调编译参数。

**核心技术结论：** `LlvmBitcodeCompiler.kt` 调用 `LLVMTargetMachineEmitToFile(..., LLVMObjectFile, ...)` 发射 object，并在错误路径释放 LLVM message；`ObjectFiles` phase 的输入从 bitcode/object 路径改为 `LLVMModuleRef + BitcodeCompiler + Path`。因为 object emission 可能修改 module，原本在外部 clang 前后的 IR dump/verify 也必须提前。目标机初始化包含 AsmPrinter/AsmParser；GlobalISel 目前只在 Darwin 启用，因为 Linux x86-64 观察到巨大内存峰值，其他平台退回 SelectionDAG；Windows/Linux 保持 function/data sections，Windows/Android 保留 emulated TLS 配置。

```kotlin
val error = LLVMTargetMachineEmitToFile(
    targetMachine, llvmModule, outputPath, LLVMObjectFile, errorMessage.ptr
)
if (error != 0) {
    val message = errorMessage.value?.toKString()
    LLVMDisposeMessage(errorMessage.value)
    error(message ?: "LLVM object emission failed")
}
```

**最有价值的实验、源码与 benchmark 细节：** 在大型 `animeko` 工程上，总构建时间 `287.0s → 220.0s`（-23.4%，1.30×）；link task `224.8s → 167.5s`（-25.5%，1.34×）；各 cache build 合计 `213.3s → 157.4s`（-26.2%，1.36×）。最直接对应设计的 `ObjectFiles` phase 从 `77.0s` 降到 `34.3s`，减少 55%，约 2.24×；最终 link 仅 `8.3s → 7.2s`，说明收益主要来自消除 per-file bitcode 往返与进程启动，而不是链接器突然变快。32/64 位与平台差异通过目标机配置显式保留，但 PR 仍为实验性，尤其 Linux x86-64 的 GlobalISel 内存峰值说明“把工具搬进进程”也会改变峰值 RSS 与故障隔离边界。

**适合的工程师背景：** 熟悉 Kotlin/Native、KLIB/增量缓存、LLVM C API，或维护编译器中间产物、外部工具链进程与缓存流水线的工程师。

**预计阅读收益：** 约 50–70 分钟；能掌握如何用 phase 级数据判断磁盘与进程边界是否值得移除，以及怎样在原位 object emission 下重新安置 verify、dump、目标机与错误处理。

## 03 · RISC-V ZGC：为常量 `null` 存储跳过无意义的地址合成

**原文与日期：** OpenJDK RISC-V/ZGC 贡献者，2026-10-30（中原标准时间）；[OpenJDK PR #33644](https://github.com/openjdk/jdk/pull/33644)、[JDK-8396162](https://bugs.openjdk.org/browse/JDK-8396162) 与 [Webrev 00](https://webrevs.openjdk.org/?repo=jdk&pr=33644&range=00)。

**为什么值得读：** ZGC 的普通指针存储必须把地址编码成带颜色的 zpointer。对常量 `null`，通用 RISC-V 路径仍先把零物化到寄存器、按 `ZPointerLoadShift` 左移，再 OR 上可重定位的 store-good color；前两步没有信息量。补丁通过 C2 matcher 的专用规则消除它们，同时保留 pre-barrier、慢路径、relocation 与内存序，适合学习“局部删指令，不能删语义边界”的优化方法。

**核心技术结论：** 新增 `zStorePNull` 与 `zStorePVolatileNull`，直接匹配 `StoreP mem immP_0`。`z_color` 与 `store_barrier_fast` 接受 `noreg` 作为新地址：空引用路径直接把 relocatable good color 装入目标寄存器，不再执行 shift/OR；非空引用继续走原路径。volatile 与普通规则分开，避免把内存序差异藏在同一个模板里。

```text
通用路径：  materialize 0 → slli ZPointerLoadShift → or store_good_color
专用路径：  load relocatable store_good_color
```

**最有价值的实验、源码与 benchmark 细节：** jtreg 新增 7 类方法：普通字段、volatile、release、数组、volatile 数组、先存非空再存空、分配后存空；IR 断言要求 `NULL_STORE=1`，并禁止零地址物化节点，执行阶段还穿插 `System.gc()`。较早基线 `de15ba…` 上完成 RISC-V fastdebug 交叉构建、8 组功能/GC stress 与 IR 验证；QEMU + `Zalasr` 下 7 个方法、9 条 IR 规则全部通过，未修改 JVM 会按预期在优化断言上失败。固定到 SpacemiT K3 X100 的 6 组配对 JMH 中，普通 null 字段存储耗时下降 13.58%（配对 95% CI 12.66–14.49%），null 数组元素下降 7.45%（CI 6.96–7.93%）；volatile 与非 null 控制组没有一致变化。数字来自热数据、无分配微基准，不能外推应用吞吐。更重要的是，当前 PR 基线 `6cf31a…` 只确认 fastdebug/release 的 ADLC 生成与编译通过，完整运行验证仍待补齐；因此正文不把早期基线的测试包装成当前提交已全部通过。

**适合的工程师背景：** 熟悉 HotSpot C2 AD 文件、ZGC colored pointers、RISC-V 汇编与 IR framework，或正在为 JIT 增加常量特化存储规则的工程师。

**预计阅读收益：** 约 45–65 分钟；能看到 matcher、barrier assembler、relocation 与 jtreg IR 断言怎样共同证明一个两三条指令级优化，并学会把当前基线与历史 benchmark 的证据强度分开。

## 本期结论

三篇材料都在修复同一种工程性浪费：局部退出被误当作全局结束、活 LLVM module 被迫跨磁盘和进程往返、已知为零的地址仍走完整着色合成。真正可迁移的方法不是“删一步”，而是先找出必须保持的边界：调度公平性、IR 验证与目标机配置、GC barrier 与内存序；再用对照组、产物验证和基线声明证明优化没有越界。
