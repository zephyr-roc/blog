## 01 · Simplifying Weak Reference Processing in ZGC

**作者与日期：** Fredrik Hammarberg，2026-06-11。

**为什么值得读：** 这不是“ZGC 很快”的泛泛介绍，而是一篇和 Oracle GC 团队合作完成的硕士论文工程总结。文章把弱引用从发现、链入 `discovered` 列表、进入 pending list，再到 `ReferenceHandler` 的整条路径拆开，并对四种改造分别测量。

**最核心的技术结论：** ZGC 的弱引用成本更像是表示方式问题，而不只是流水线调度问题。把侵入式链表改为连续动态数组，并联合消除 load barrier、虚调用和不必要的 CAS，可让 `Concurrent Process Non-Strong` 阶段在单对象测试中下降 81%，在多对象测试中下降 57%。但这并不等价于整次 GC 快 81%：对应的 major collection 改善只有约 8% 和 2%。用字段级弱语义替代 `WeakReference` 对象，反而能跨多个 GC 阶段减少工作，整次 major collection 在两组测试中下降 41% 和 28%。

**最有价值的实验与源码细节：** 两组基准分别构造 2,000 万个 holder 和 200 万个带可变 payload 的对象；使用 100 GB 堆、Generational ZGC、`InitialTenuringThreshold=1`，在 AMD EPYC 9454P 节点上运行 250 次测量，并用 `taskset` 隔离 CPU。文章还诚实列出辅助 GC 内存代价：某些动态数组组合的峰值辅助内存会放大数倍。这一点能防止读者把局部阶段的胜利误判成免费的全局优化。

**适合谁：** 做 JVM 性能、缓存/元数据系统、GC 调优，或正在阅读 HotSpot ZGC 源码的中高级 Java 工程师。

**预计阅读收益：** 学会把 GC 优化拆成“表示、访问局部性、barrier、原子操作、整次回收占比”五个层次，并建立局部指标必须回到端到端指标复核的习惯。

**原文：** [Simplifying Weak Reference Processing in ZGC](https://inside.java/2026/06/11/thesis-simplify-weak-reference-processing-zgc/)

## 02 · One Giant Leap: 95% Less Sampling Cost

**作者与日期：** Jonas Norlinder，2026-01-01 发布，2026-03-21 更新。

**为什么值得读：** 它完整展示了一个 HotSpot 性能问题如何一路追进 Linux ABI，再落成 OpenJDK 补丁。问题表面上只是 `ThreadMXBean.getCurrentThreadUserTime()`，实际瓶颈却来自每次读取 `/proc` 时内核生成文本、复制到用户态，再由 JVM 把文本解析回整数。

**最核心的技术结论：** 高频监控不能默认把“标准接口”当作低成本接口。将 `/proc` 文本路径替换为 `clock_gettime()` 的直接调用后，当前线程 user CPU time 的采样获得约 20 倍加速；文章在另一台机器上观察到最坏样本从约 1 ms 降到 0.054 ms，降幅约 95%。

**最有价值的实验与源码细节：** 精华不只在数字，而在作者如何编码 Linux 的 per-thread CPU clock ID、绕过文档不充分的 ABI，并用多台机器和尾延迟而非单一平均值验证改动。文章还把 `/proc` 路径的锁、格式化、复制和解析画成调用链，让“为什么一次看似简单的采样会污染被观测系统”变得可定位。

**适合谁：** 使用 JFR、profiler、ThreadMXBean、线程级计费或调度指标的性能工程师，以及需要在 Java 与 Linux 内核边界排障的人。

**预计阅读收益：** 获得一套跨 JVM/系统调用/内核 ABI 的性能调查范式，并更谨慎地评估可观测性的 observer effect。

**原文：** [One Giant Leap: 95% Less Sampling Cost](https://norlinder.nu/posts/User-CPU-Time-JVM/)

## 03 · How to speed up the Rust compiler in July 2026

**作者与日期：** Nicholas Nethercote，2026-07-31。

**为什么值得读：** 这是 rustc 性能工作的阶段性账本，不靠单个“神奇优化”讲故事，而是把数月内真正进入编译器的改动、对应 PR 和 rustc-perf 结果串起来。对 Java 工程师也很有价值，因为它展示了大型编译器如何用稳定的基准基础设施管理持续的小幅回归与收益。

**最核心的技术结论：** 2025-12-03 至 2026-07-29，rustc-perf 记录到平均 wall time 改善 5.59%。其中 rustdoc 是大头，相关基准的平均 wall time 改善 37.92%；剔除 rustdoc 后仍有 2.90%。这说明编译器性能提升通常来自许多可验证的小改动，以及对训练集、数据表示和重复工作的持续清理。

**最有价值的实验与源码细节：** 文中逐个链接到 PR：一组改动减少 rustdoc 处理 impl 的工作量；把 rustdoc benchmark 加进 PGO 训练集带来平均 2.85%、最佳超过 6% 的 wall-time 改善；另一个改动不再排序很长的生成 HTML，而改用更短的文本 key，部分 benchmark 的指令数下降超过 6%。这里最值得复用的不是某个 Rust 技巧，而是 `wall time + instruction count + cycles` 交叉验证的方式。

**适合谁：** 维护大型 Java/Kotlin 构建、编译器或代码生成器，关注 Gradle/Kotlin 编译耗时，或者想理解 PGO 与基准治理的工程师。

**预计阅读收益：** 学会区分 wall time、指令数和 CPU cycles 的信号强弱，并把“减少重复工作、缩短排序键、校准 PGO 训练集”迁移到自己的工具链优化中。

**原文：** [How to speed up the Rust compiler in July 2026](https://nnethercote.github.io/2026/07/31/how-to-speed-up-the-rust-compiler-in-july-2026.html)

## 04 · The Journey to Compose Hot Reload 1.0.0

**作者与日期：** Sebastian Sellmair、Azat Abdullin，2026-01-13。

**为什么值得读：** 这是少见的把 Kotlin 编译器、Compose IR、JVM Instrumentation、DCEVM、GC 状态迁移和 Gradle 增量构建放在同一条实现链上讲清楚的文章。它不是功能宣发，而是在解释“任意修改类结构后，正在运行的对象和 UI 状态究竟怎么活下来”。

**最核心的技术结论：** 热重载不是简单替换 `.class`。JetBrains Runtime 先在 side universe 验证和加载新类，再借一次特殊 GC pass 迁移对象并更新引用；旧的 JIT 机器码可能失效，因此需要去优化，之后再由 JIT 重新升温。Compose 侧还要从字节码中恢复 group 与方法依赖，只让真正受影响的 group 失效，才能尽可能保存状态。

**最有价值的源码与字节码细节：** Java agent 通过 `Instrumentation.redefineClasses` 驱动 DCEVM；Gradle 插件对 hot classpath 中的 `.class` 做 checksum 快照并增量比较；agent 用 ASM 识别 `startRestartGroup` / `endRestartGroup`、group key、控制流和方法依赖。文章还展示了 Kotlin 编译器为稳定 lambda 名称所做的真实改动：Compose singleton lambda 自 2.1.20 起使用稳定 group key，indy lambda 自 2.2.20 起改为作用域内稳定编号，避免一次局部编辑引发大面积类名漂移。

**适合谁：** Kotlin/JVM、Compose Multiplatform、Java agent、字节码工具、IDE 或增量编译方向的中高级工程师。

**预计阅读收益：** 把“热重载”从一个开发体验功能还原成运行时对象迁移、JIT 去优化、字节码分析和增量构建协同问题，并理解 Kotlin 编译器为何会为工具链稳定性改变代码生成策略。

**原文：** [The Journey to Compose Hot Reload 1.0.0](https://blog.jetbrains.com/kotlin/2026/01/the-journey-to-compose-hot-reload-1-0-0/)

## 本期结论

四篇文章有一个共同点：性能问题很少停留在 API 表面。弱引用会一路落到对象表示与 barrier，线程采样会落到 Linux ABI，编译耗时会落到数据表示与 PGO 训练集，热重载则会穿过编译器、字节码、GC 和 JIT。真正值得长期跟踪的文章，应该能把这条因果链闭合，并留下足够信息让读者复查。
