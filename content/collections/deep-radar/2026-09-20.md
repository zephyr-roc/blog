## 01 · Rust：把 Polonius 热路径上的查表、分支与重复访问一起移出循环

**原文与日期：** Jack Huey，2026-09-20 00:50（中原标准时间）；[rust-lang/rust PR #163027](https://github.com/rust-lang/rust/pull/163027) 与 [rustc-perf 指令计数对比](https://perf.rust-lang.org/compare.html?start=36b04f3ad12a98b1a3cf9efe5313306ef7d5848d&end=1d91cb490050ad9537ce8f1194876a97f435a15a&stat=instructions:u)。补丁仅修改 `compiler/rustc_borrowck/src/polonius/constraints.rs`，增加 80 行、删除 153 行；截稿时已由 reviewer `lqd` 批准，但 Rust 合并队列因 GitHub outage 暂停。

**为什么值得读：** 这是一份很干净的“图遍历常数项优化”样本。它没有改变 Polonius 的可达性语义，而是连续消除三类位于每个 loan、每个 node、每条 successor 边上的固定成本：整数密集键仍走哈希表、visited 先查再插、同一节点的 variance/direction 在前后向边处理中重复推导。每一项单看都小，但它们恰好乘在借用检查图的遍历规模上。

**核心技术结论：** 第一，`RegionVid` 是从 0 开始的密集索引，`logical_edges` 因此从 `FxHashMap<RegionVid, FxIndexSet<RegionVid>>` 改成 `IndexVec`，读取不再哈希；构建时用 `ensure_contains_elem` 延长向量。第二，把 successor 的 visited 判断从 `contains` 加 `insert` 两次查表，收敛为一次 `insert` 的布尔返回值。第三，先按当前 region 算一次 `liveness_direction`，再分别守卫 forward/backward 分支；原来的两个 helper 及其重复的 liveness、variance 查询被内联删除。

```rust
// 旧：两次哈希集合查询
if !visited.contains(&succ) {
    stack.push(succ);
    visitor.on_successor_discovered(node, succ);
}

// 新：一次插入同时回答“此前是否存在”
if visited.insert(succ) {
    stack.push(succ);
    visitor.on_successor_discovered(node, succ);
}
```

这里还有一个容易漏看的正确性边界：起始节点现在必须在 `push` 前先放入 `visited`。否则把去重移动到“发现 successor”之后，图上的回边会再次把根节点压栈。对于 universal region，方向直接固定为 `Forward`；其他 region 则从 `live_region_variances` 读取，缺失 variance 时仍保守退化为 `Bidirectional`，没有借性能优化缩小可达集合。

**最有价值的实验、源码与 benchmark 细节：** 官方 rustc-perf 以 Linux `instructions:u` 作为主要判定指标。17 个 primary 样本全部改善，平均 `-0.4%`、范围 `-1.0%` 到 `-0.2%`；9 个 secondary 样本平均 `-0.3%`、范围 `-0.5%` 到 `-0.2%`，两组均没有指令数回退。bootstrap 从 497.193 秒降至 495.146 秒，缩短 0.41%；artifact size 从 408.84 MiB 增至 408.91 MiB，回退 0.02%。

| 指标 | 结果 | 解读 |
| --- | ---: | --- |
| Primary 指令数 | 17 个显著样本，均值 -0.4%，范围 -1.0%～-0.2% | 最可靠主结论，无回退样本 |
| Secondary 指令数 | 9 个显著样本，均值 -0.3%，范围 -0.5%～-0.2% | 方向一致 |
| Max RSS | 1 个 primary 样本 -2.7% | 样本少且该指标噪声较大，只作线索 |
| Cycles | 2 个 primary 样本平均 +33.1%，范围 +2.2%～+64.0% | 与稳定的指令数相冲突，不能宣称 wall-clock 普遍加速 |
| Bootstrap | 497.193s → 495.146s | -0.41%，但未给重复次数与误差 |
| Artifact | 408.84 → 408.91 MiB | +0.02%，保留负向指标 |

最值得迁移的不是 `IndexVec` 这个具体容器，而是辨认循环嵌套层级：只依赖 node 的方向判定应放在 successor 枚举之外；“是否首次发现”应由集合插入一次完成；密集 newtype index 不该默认支付哈希成本。反过来，cycles 的明显回退和 instruction count 的稳定改善并存，说明微架构噪声、调度或测量环境仍需二次验证；在看到 wall-clock 多轮结果之前，只能稳妥地说“执行的编译器指令更少”。

**适合的工程师背景：** 熟悉 rustc MIR/borrowck、Polonius、CFG 可达性或高频图算法，希望学习如何在不改变语义的前提下压缩查表与分支成本的编译器工程师。

**预计阅读收益：** 约 45–70 分钟；能完整理解密集索引数据结构、DFS 去重时机、variance 驱动的双向 liveness，以及如何同时阅读 rustc-perf 的主指标与相冲突的负向指标。

## 本期结论

Polonius 这次改动把三个“小常数”放回正确的层级：密集 ID 用直接索引，首次访问用一次集合插入判定，节点属性只在节点级计算一次。指令数结果跨 26 个显著样本方向一致，但 cycles 的负向数据提醒我们不能把它包装成未经验证的 wall-clock 提升。硬件侧则继续坚持缺价留白：过期报价可以构成历史曲线，不能冒充当前价格。
