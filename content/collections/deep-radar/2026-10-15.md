## 01 · OpenJDK：让 SVE 在写回内存时直接完成窄化

**原文与日期：** Boris Ulasevich，2026-10-15 07:53（中原标准时间）；[OpenJDK PR #33373](https://github.com/openjdk/jdk/pull/33373)、[完整源码 diff](https://github.com/openjdk/jdk/pull/33373/files) 与 [JBS JDK-8392998](https://bugs.openjdk.org/browse/JDK-8392998)。

**为什么值得读：** C2 已能把 `int[]` 到 `byte[]`/`char[]` 的逐元素转换向量化，但 AArch64 SVE 旧代码生成会先用 `xtn` 把 vector register 窄化，再用普通 `str` 写回。SVE 的 `st1b` 与 `st1h` 本身就能从 32-bit lane 取低 8/16 位存储，独立窄化指令、临时结果和对应依赖链都是多余工作。这个改动很适合迁移到 SIMD 后端优化：不要只在算术 IR 中找冗余，也要检查 load/store 是否已经融合类型转换语义。

**核心技术结论：** 补丁在 AArch64 C2 `.ad` 机器描述中新增 `storeV_narrow_ItoB` 与 `storeV_narrow_ItoS`，匹配 `StoreVector(VectorCastI2X(src))`；当 `UseSVE > 0` 且 vector 宽度等于 `MaxVectorSize` 时，直接调用 `loadStoreA_predicated()`，以源元素 `T_INT`、内存元素 `T_BYTE`/`T_SHORT` 选择窄化 store。它还新增与目标内存元素缩放一致的 4-bit signed-offset operand，避免把 int lane 宽度错误套到 byte/short store 地址编码上，并用 IR framework 节点检查确保规则实际命中。

```text
旧路径：int lanes ── xtn ──> byte/short lanes ── str ──> memory
新路径：int lanes ─────────────── st1b/st1h ──> memory
```

**最有价值的实验、源码与 benchmark 细节：** 作者在 Graviton4、SVE 128-bit、数组长度 1,024、JMH `avgt` 9 次采样下给出：

| Benchmark | 修改前 | 修改后 | 延迟变化 | 加速比 |
| --- | ---: | ---: | ---: | ---: |
| `VectorSubword.intToByte` | 78.043 ± 0.701 ns/op | 65.432 ± 0.088 ns/op | -16.16% | 1.193× |
| `VectorSubword.intToChar` | 72.976 ± 0.296 ns/op | 66.978 ± 0.442 ns/op | -8.22% | 1.090× |

源码证据不只是新增两条选择规则：`IRNode` 同步加入 `AARCH64_STORE_V_NARROW_I2B/I2S`，`TestVectorizeTypeConversion` 在检测到 SVE 时要求窄化 store 节点出现，从而把“生成了目标指令形态”纳入回归测试。限制也很清楚：结果来自单台 Graviton4、固定 128-bit SVE 与 1,024 元素热循环；PR 尚未完成两位 reviewer 要求，不能外推到所有 SVE 宽度、数组长度或已发布 JDK。

**适合的工程师背景：** 熟悉 HotSpot C2 SuperWord/Vector API、AArch64 SVE 或正在维护 LLVM/GCC 类指令选择器的编译器工程师。

**预计阅读收益：** 约 30–45 分钟；能掌握如何从 ISA 的 narrowing-store 语义反推 matcher 规则、地址 operand 与 IR regression test，并用 JMH 验证少一条向量指令是否真正缩短关键路径。

## 02 · Linux：用 RCU 延迟复用消除页缓存小读的 folio refcount 热点

**原文与日期：** Linus Torvalds，2026-10-14 05:26（中原标准时间）；[LKML v3 补丁组](https://lkml.iu.edu/2610.1/13146.html)、[补丁源码与完整实验记录](https://mirrors.hust.edu.cn/git/linux.git/commit/?h=noref-filemap-read-with-llm) 与 [LWN 技术审阅](https://lwn.net/Articles/1100449/)。

**为什么值得读：** 多线程反复 `pread()` 同一个已缓存小文件时，数据本身只读，传统 filemap 路径却必须为 folio 获取和释放引用。`filemap_get_read_batch()` 的 locked compare-exchange 与 `filemap_read()` 的 atomic decrement 会让所有 CPU 写同一个 `struct page` cacheline；随着核心数增加，瓶颈从内存拷贝转成 cacheline ownership 往返。补丁没有尝试把 refcount 原子操作“做快一点”，而是改变对象复用协议：读者不再持有引用，页离开 page cache 后必须等 RCU grace period 才能重新分配。

**核心技术结论：** 热 folio 被标记为 `PG_rcu_free`；无引用读取路径在 `rcu_read_lock()` 内关闭用户页 fault，确认 folio 仍匹配 xarray 与文件偏移后直接 `copy_page_to_iter()`。folio 从 page cache 移除时先进入 per-CPU pending/batch 队列，等 grace period 后才真正归还 allocator；待回收页超过阈值时主动加速 RCU，分配器也在内存紧张时考虑这些“已释放但尚不可复用”的页。只有被识别为热读的 folio 承担延迟释放，避免把全部 page-cache eviction 都拖入 RCU 队列。

**最有价值的实验、源码与 benchmark 细节：** 64 线程 Ryzen Threadripper 在同一缓存页执行小读：

| 指标 | 基线 | RCU 无引用读取 | 变化 |
| --- | ---: | ---: | ---: |
| 吞吐 | 13.3M reads/s | 304M reads/s | 22.86× |
| cycles/read | 19,857–19,939 | 735–736 | 约 -96.3% |
| instructions/read | 1,094–1,101 | 959 | 约 -12.5% |

较早的 8 线程、16-byte `pread()` 样本也从约 9.9–10.4M 提升到 30–33M reads/s；`perf c2c` 的 load HITM 从 30,538 降到 101，直接支持“共享 refcount cacheline 是主因”，而不只是 wall-clock 巧合。正确性压力测试在约 `10^8` 次 eviction-race 读取与 115 万次 partial-fault 读取中没有发现坏数据；用于验证测试灵敏度的“立即复用”对照分别捕获 12 和 138 次坏读。

代价同样重要。16-byte 读取遇到缺失用户页时，cycles 从约 4,117–4,188 上升到 6,543–6,593，约回退 58%；1 MiB 大读的 instruction count 增加约 6%。早期只做延迟释放时，等待 grace period 的内存可达 565 MiB、峰值约 1.0–1.2 GiB；加入批处理与主动推进后，4 CPU 样本降至 15 MiB，避免了早期版本在 4/8 CPU VM 上的 OOM。LWN 评审还指出 `filemap_read_rcu_batch()` 在 folio 被替换且 `i_size` 扩展时可能暴露未写入数据的竞态；补丁仍在演进，22.86× 是极端共享页上限，不是普通文件服务器的收益预测。

**适合的工程师背景：** 熟悉 Linux page cache、folio/xarray、RCU 与 `perf c2c`，或正在处理只读热对象 refcount 扩展性问题的内核/运行时工程师。

**预计阅读收益：** 约 60–80 分钟；能学会用 HITM 将吞吐塌陷定位到 cacheline ownership，并理解“省掉读侧引用”必须同时重构对象回收、内存压力反馈、page fault 与竞态验证。

## 本期结论

两项工作都把“中间状态”折叠进更强的底层语义：SVE store 直接承担 lane 窄化，RCU grace period 直接承担无引用读取后的生命周期安全。前者是局部指令融合，后者是跨 allocator、page cache 与 fault handling 的协议重构；共同的工程方法是先用源码与硬件计数器证明中间步骤确实是瓶颈，再把正确性条件写进 matcher、回收队列和回归测试。性能数字必须连同适用边界阅读：一个只覆盖单款 SVE 机器，另一个刻意构造最严重的共享 cacheline 争用。
