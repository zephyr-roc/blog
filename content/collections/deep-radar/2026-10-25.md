## 01 · Linux VSwap：让页表槽位不再等同于物理 swap 槽

**原文与日期：** Nhat Pham，2026-10-21 14:03（中原标准时间）；[LKML v6 cover letter](https://lore.kernel.org/all/20261021060323.553433-1-nphamcs@gmail.com/)、[LWN 邮件镜像与完整线程](https://lwn.net/ml/all/20261021060323.553433-1-nphamcs@gmail.com/)。系列共 12 个补丁、修改 26 个文件，增加 2,291 行、删除 293 行。

**为什么值得读：** 传统 swap entry 同时承担页表标识、swap cache key、cgroup 索引与磁盘槽地址；这在“交换等于落盘”时很高效，却迫使只驻留 zswap、零页或 cache-only folio 的页面也预占物理 swap 槽。VSwap 把 PTE 中的虚拟槽与实际后端拆开，使 zswap 可以动态增长、按需落盘，又不在后端迁移时扫描 PTE/rmap。这是一篇少见的、同时覆盖数据结构、并发同步、cgroup 记账和生产 A/B 的内存管理材料。

**核心技术结论：** 启用 `vswap=on` 后，可交换匿名页先从特殊虚拟设备取得槽位；每个动态 cluster 在原有 `swap_cluster_info` 外增加 `virtual_table`。表项低 3 位编码后端类型：`000` 表示尚无独立后端，`001` 指向 `zswap_entry`，`010` 保存物理 swap 的 type/offset。物理 cluster 中的 VSwap 标记反向指回虚拟 entry，因此 zswap writeback 迁移到磁盘时无需修改页表。后端切换继续由 swap cache 与 folio lock 串行化；cgroup v2 的 `memory.swap.current` 只在虚拟 entry 真正获得物理槽时计费。

```c
struct swap_cluster_info_dynamic {
    struct swap_cluster_info ci;
    unsigned int index;
    struct rcu_head rcu;
    atomic_long_t *virtual_table; /* 8 bytes per slot */
};

/* low three bits: NONE=000, ZSWAP=001, SWAPFILE=010 */
```

**最有价值的实验、源码与 benchmark 细节：** x86-64、52 核、zstd zswap 环境中，memhog 在 16GB RAM 上单线程分配 48GB，20 轮均值从 `124.05±11.64s` 降到 `118.57±15.68s`（-4.4%）；剔除最好与最差轮后为 `123.75±10.39s → 116.06±8.22s`（-6.2%），但方差仍然很大。usemem 在 32GB RAM 上分配 56GB、16 轮，吞吐只提高 1.0%，而 free 阶段从 `7669±146ms` 降到 `6439±111ms`（-16.0%）。52 worker、`memory.max=3GB` 的内核构建则揭示代价：VSwap on 的 wall time `165.58±0.45s → 166.01±0.58s`（+0.3%），system time +1.6%；补丁存在但关闭时 system time甚至 +2.4%。Instagram django A/B 报告吞吐持平、请求延迟降低约 1–3%，并消除 zswap 用户的 swapfile 占用，但未公开原始样本量。最重要的边界是：上述数字来自 xarray 版本，第 12 个 `VM_SPARSE` 替代实现只做过简单 stress test，不能继承这些性能结论。

**适合的工程师背景：** 熟悉 Linux MM、zswap、swap cache、folio lock、memcg/cgroup v2，或正在设计压缩内存、分层内存与无盘设备内存回收的内核工程师。

**预计阅读收益：** 约 75–100 分钟；能理解如何在不扫描页表的前提下虚拟化 swap 地址空间、如何编码双向映射与同步边界，以及为什么“关闭功能不回退”也必须进入验收矩阵。

## 02 · Kotlin/Native：删除已经不影响输出的 proto 遍历

**原文与日期：** JetBrains Kotlin 团队，2026-10-23 18:53（中原标准时间）；[Kotlin PR #9233](https://github.com/JetBrains/kotlin/pull/9233)、[KT-90643 对应源码 diff](https://github.com/JetBrains/kotlin/pull/9233/files) 与引入历史行为的 [commit 873df4c](https://github.com/JetBrains/kotlin/commit/873df4c70f94)。

**为什么值得读：** 性能问题不在序列化本身，而在一段“看似只做校验”的遗留路径：`buildSerializedClassFields` 为每个嵌套类重新反序列化顶层声明，再沿父类 proto 找回目标类并扫描字段。自 KT-52512 之后，这些中间结果没有任何一个进入最终输出，却仍让包含大量嵌套模型的 cache build 变成二次复杂度。补丁只删一个文件中的 48 行左右代码，却获得数量级收益。

**核心技术结论：** 真实输出的 `SerializedClassFields` 已经来自 IR 中的 `fields`，`ClassFieldsDeserializer` 又按索引而非字段名匹配；因此 proto 字段重名检查、父 proto 的 `findClass` 以及从 outer proto 解码 `thisReceiver` 都不再提供语义保障。保留 `getFileDeserializationState(signature.topLevelSignature())` 获取文件引用，并依靠现有 `require(irClass.isInner)` 守住 inner-class 不变量即可。

```kotlin
// 旧路径：每个 nested class 都从 top-level declaration 重新下钻
- val protoDeclaration = fileReader.declaration(declarationIndex)
- var protoClass = protoDeclaration.irClass
- protoClass = protoClass.findClass(...)
- protoClass.declarationList.forEach { /* collect proto fields */ }

// 新路径：输出只使用 IR fields，proto walk 整段删除
val fileDeserializationState =
    deserializer.getFileDeserializationState(signature.topLevelSignature())
```

**最有价值的实验、源码与 benchmark 细节：** 一个包含 2,000 个 nested models 的类，Kotlin/Native cache build 从 `141s` 降到 `11s`，约 12.8 倍，耗时减少 92.2%。作者没有只用时间证明等价：195 个 box tests 分别以 `STATIC_EVERYWHERE` 与 `STATIC_PER_FILE_EVERYWHERE` 运行，另跑 129 个 cache tests；相同 klib 的 `class_fields` 以及其余 IR cache 文件均与 master 字节级一致。源码 diff 还能直接看到 `BinaryNameAndType`、`ProtoField`、`fileReader`、`symbolDeserializer` 与整个 `protoFieldsMap` 被删除，证据与复杂度解释完全对齐。

**适合的工程师背景：** 熟悉 Kotlin/Native、KLIB/IR serialization、编译缓存，或正在排查编译器前后端中“重复解析 + 嵌套结构”导致的规模化退化的工程师。

**预计阅读收益：** 约 35–50 分钟；能学会从“某项校验是否仍影响产物”反向做数据流审计，并用字节级产物对照为删代码型性能优化建立强证据。

## 03 · HotSpot SVE `String.indexOf`：先筛首尾字符，再验证候选

**原文与日期：** Nick Gasson / Arm，2026-10-21 21:11（中原标准时间）；[OpenJDK PR #33493](https://github.com/openjdk/jdk/pull/33493)、[JDK-8393101](https://bugs.openjdk.org/browse/JDK-8393101) 与 [Webrev 00](https://webrevs.openjdk.org/?repo=jdk&pr=33493&range=00)。

**为什么值得读：** 这不是简单把 NEON 换成更宽的寄存器。实现必须兼容 Latin1、UTF-16 与 UTF-16 haystack/Latin1 needle 混合编码，处理任意 needle 长度、尾向量 predicate、多候选冲突和等长字符串快路；同时两代 Neoverse 对同一组 JMH 的响应差异巨大，正好展示可伸缩向量代码为何不能只报最好数字。

**核心技术结论：** C2 在 `UseSVE > 0` 时选择新的 `string_indexof{LL,UL,UU}_sve` AD 规则。MacroAssembler 先广播 needle 的首尾字符，对 haystack 两个对应窗口分别执行 `sve_cmp`，再以 `sve_ands` 只保留同时命中的 lane；`sve_brkb` 与 `sve_cntp` 找出最低候选，随后用 predicated load 逐向量验证整个 needle。失败时用 `sve_brka`/`sve_bics` 清掉已经验证的候选并继续；长度为 1 则回退现有 `string_indexof_char_sve`。

```cpp
sve_cmp(EQ, pred_first, variant, active, haystack_vec, first_needle_vec);
sve_cmp(EQ, pred_last,  variant, active, haystack_last_vec, last_needle_vec);
sve_ands(pred_first, active, pred_first, pred_last);

sve_brkb(lowest, active, pred_first, false);
sve_cntp(lane_offset, variant, lowest, lowest);
```

**最有价值的实验、源码与 benchmark 细节：** PR 以 commit `64e0cf4` 为基线运行 `TEST="micro:IndexOf.*"`，表中 delta 是 `avgt ms/op` 倍数，越低越好。`successBig` 在 Neoverse V2/V3 分别为 `0.391×/0.376×`，即约 2.56/2.66 倍加速；V3 的 `searchHugeLargeSubstringNoMatch` 为 `0.023×`（约 43.5 倍），UTF-16 版本 `0.029×`（约 34.5 倍）。但 V2 的同一无匹配用例只有 `0.457×`，而 `searchHugeMiddleMatch` 反而为 `2.112×`（慢 111.2%）；V3 的 `search16HugeNoMatch` 为 `1.456×`（慢 45.6%），短 substring 也有约 7–8% 回退。工程结论不是“SVE 必然更快”，而是首尾过滤对长 needle 和拒绝型输入非常有效，候选密度、微架构与尾部路径决定回退风险。

**适合的工程师背景：** 熟悉 HotSpot C2 matcher、AArch64 SVE predicate、Compact Strings，或在 JVM/标准库中维护 SIMD 字符串搜索 intrinsic 的工程师。

**预计阅读收益：** 约 60–80 分钟；能掌握可伸缩向量字符串搜索的候选生成/验证结构、混合编码加载方式，以及用完整矩阵而非峰值加速判断是否值得合入。

## 本期结论

三篇材料的共同点是先辨认“身份”与“载体”是否被错误绑在一起：VSwap 把页表身份从物理后端解耦，Kotlin/Native 把真实 IR 输出从已经失效的 proto 校验解耦，SVE `indexOf` 把廉价候选筛选与昂贵全串验证解耦。迁移到工程实践时，还要保留三类反证：关闭路径是否仍有成本、产物是否逐字节等价，以及不同微架构/输入分布是否出现回退。
