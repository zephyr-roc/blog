## 01 · HotSpot：只有 barrier 真正需要时，才把 `StackChunk` 转为 GC 模式

**原文与日期：** OpenJDK HotSpot/Loom 贡献者，2026-11-13 02:38（中原标准时间）；[OpenJDK PR #33884](https://github.com/openjdk/jdk/pull/33884)、[JDK-8397224](https://bugs.openjdk.org/browse/JDK-8397224) 与 [`continuationFreezeThaw.cpp` 源码 diff](https://github.com/openjdk/jdk/pull/33884/files)。

**为什么值得读：** continuation 的 thaw slow path 并不只由 GC barrier 触发。虚拟线程持有 monitor 时，恢复 lock stack 也必须先走 slow path；旧代码随后无条件调用 `relativize_chunk_concurrently()`，把本来不需要 barrier 的 `StackChunk` 转成 GC 模式。这个状态变化会让后续 thaw 继续落在 slow path，并逐帧处理 oop，形成“因为一次非 GC 慢路径，永久支付 GC 慢路径成本”的反馈环。补丁只改动十余行，却把状态机边界、safepoint 后重读和两种并发 GC 的差异完整暴露出来。

**核心技术结论：** `_barriers` 表示当前 chunk 是否真的要求 barrier。若 `resume_operation()` 期间可能因 JVMTI 事件经过 safepoint，代码不仅重新读取 `_cont.tail()`，还必须从新 chunk 重新读取 `requires_barriers()`；随后无论是 preempted continuation 分支还是普通 thaw slow path，都只在 `_barriers` 为真时调用 `relativize_chunk_concurrently()`。monitor 恢复仍可触发一次 slow path，但不再顺带改变 chunk 的 GC 模式；下一次 thaw 因而可以回到 fast path。

```cpp
chunk = _cont.tail();
_barriers = chunk->requires_barriers();

if (_barriers) {
    relativize_chunk_concurrently(chunk);
}
```

**最有价值的实验、源码与 benchmark 细节：** 作者把 Skynet 对 `skynet()` 的调用包进 `synchronized(Thread.currentThread())`，令虚拟线程因 owned monitor 进入 thaw slow path，同时把任务数设为 1,000,000。ZGC 的 JMH average time 从 `249.090 ± 14.147 ms/op` 降到 `193.292 ± 12.015 ms/op`，即延迟下降 22.4%、等效吞吐约 1.29×；Shenandoah 从 `498.991 ± 20.858` 降到 `182.302 ± 18.351 ms/op`，延迟下降 63.5%、等效吞吐约 2.74×。两组均为 5 次计数。作者原文把 ZGC 概括为“约 30% improvement”，这里按原始时间重新计算，避免把耗时下降与吞吐提升混写。评审者原先预计 Shenandoah 收益较小，因为旧 chunk 可能仍需为 barrier patching 走慢路；实测反而更大，说明这个特定 workload 的主因是无条件 GC 模式转换，而非 barrier patching 本身。补丁另跑过 mach5 tier1–5，但尚未完成所需评审。

**适合的工程师背景：** 熟悉 Loom continuation、virtual thread monitor、ZGC/Shenandoah barrier，或正在维护“多个原因共享一条慢路径”的运行时工程师。

**预计阅读收益：** 约 35–50 分钟；能学会如何拆分“进入慢路径的原因”与“慢路径中需要改变的持久状态”，以及 safepoint 后哪些派生状态必须与 oop 一起重读。

## 02 · Rust：用 exact-match 类型等价关系跳过不可能统一的 trait impl

**原文与日期：** rustc 贡献者 Nicholas Nethercote，2026-11-11 12:53（中原标准时间）；[rust-lang/rust PR #165795](https://github.com/rust-lang/rust/pull/165795)、[rustc-perf 对比](https://perf.rust-lang.org/compare.html?start=9c5648833e5ceb667a708d53c00b83ecc9e610d5&end=56f1bf8c3136ff52cb099e93ee0abd19c800112d&stat=instructions:u) 与 [完整源码 diff](https://github.com/rust-lang/rust/pull/165795/files)。

**为什么值得读：** `simplify_type` 只能把 impl 按外层形状分桶。面对 `BitsImpl<0>` 到 `BitsImpl<1023>` 这类同一 generic ADT 的大量 const 实例，1024 个 impl 全落在同一个桶里，trait solver 仍需逐一尝试统一。新设计没有再细分一个易失控的索引键，而是定义更强但保守的 exact-match 性质：若查询 self type 与 impl self type 都满足该性质，它们能统一当且仅当 `Ty` 相等；不相等即可在候选组装前安全跳过。

**核心技术结论：** scalar，以及只含 exact-match 参数、无 region 的 ADT/tuple/array/slice 可以成为 exact-match；const 参数只接受 `usize` 的叶值，遍历预算固定为 64，超限或遇到 reference、raw pointer、alias、projection、inference variable 等类型就保守返回 false。只有桶大小至少 16 且查询 self type 为 exact-match 时才启用过滤，避免小桶为建表付出额外成本。`trait_impl_exact_match_self_tys` 查询保持与原 impl bucket 相同的长度和顺序；candidate assembly 使用过滤版 `for_each_candidate_impl`，而 auto-trait existence 等需要完整相关集合的路径仍保留原 `for_each_relevant_impl`。

```rust
if bucket.len() >= 16 && is_exact_match_ty(self_ty) {
    for (impl_id, exact_ty) in zip(bucket, cached_exact_tys) {
        if exact_ty.is_none_or(|ty| ty == self_ty) {
            visit(impl_id);
        }
    }
}
```

**最有价值的实验、源码与 benchmark 细节：** rustc-perf 的 userspace instructions 是主判据：primary 有 49 个改善，平均 `-11.9%`，范围 `-29.5%` 到 `-0.2%`；3 个轻微回退，平均 `+0.2%`，范围 `+0.2%` 到 `+0.3%`，合并 52 个变化样本后平均 `-11.2%`。secondary 有 14 个改善，平均 `-13.1%`、最好 `-33.7%`，没有统计到回退。cycles 的 primary 改善均值为 `-7.4%`，但 secondary 仍有 1 个 `+3.2%` 回退；Max RSS 的 primary 混合结果为 `-2.4%`，同时存在 `+1.2%` 到 `+1.5%` 的两个回退。bootstrap `482.775s → 485.777s`，反而增加 0.62%；artifact 仅 `-0.01%`。作者本地未进入 rustc-perf 的 `hybrid-array-0.4.13` 指令数下降 46%、cycles 下降 27%，应视为补充而非官方套件结论。PR 仍是 draft，作者明确表示还要补测试并征求 trait solver 团队对复杂度的意见。

**适合的工程师背景：** 熟悉 rustc trait solver、fast reject、specialization graph、const generics，或维护大规模规则/实例候选系统的编译器工程师。

**预计阅读收益：** 约 50–70 分钟；能掌握如何从“相等即可判定可统一”的强不变量构造安全快拒绝、如何用阈值与遍历预算限制优化成本，以及怎样同时报告主指标与 bootstrap 回退。

## 本期结论

两篇材料都在修复“共享慢路径让无关工作变成持久成本”：HotSpot 把 monitor 恢复与 GC barrier 模式转换解耦，rustc 则在完整 trait 候选集合与 solver 真正需要访问的候选之间增加可证明安全的 exact-match 过滤。可迁移的方法不是看到慢路径就跳过，而是先找出足够强的状态不变量——`requires_barriers()` 与 exact-match 类型等价关系——再用保守回退、阈值和负向 benchmark 约束优化边界。
