## 01 · OpenJDK：让 AES-CBC 解密批次随 RISC-V VLEN 扩展

**原文与日期：** OpenJDK RISC-V 贡献者，2026-11-03 19:51（中原标准时间）；[OpenJDK PR #33693](https://github.com/openjdk/jdk/pull/33693)、[JDK-8396510](https://bugs.openjdk.org/browse/JDK-8396510) 与 [HotSpot 源码 diff](https://github.com/openjdk/jdk/pull/33693/files)。

**为什么值得读：** 旧 stub 无论硬件 VLEN 是 128、256、512 还是 1024 位，每轮都只解一个 16 字节 AES block，宽向量的大部分 lane 空着。新实现保持 LMUL=1，却让每批覆盖 1、2、4 或 8 个 block，并且没有破坏 CBC 的前块依赖、尾批处理和 input/output 重叠语义。它比“把循环改成 RVV”更有价值：正文把依赖链如何变成向量、怎样证明 in-place 安全、固定开销何时反噬短消息都交代清楚。

**核心技术结论：** 循环以 e32/m1 设置运行时 VL，一个 AES block 对应四个 32 位元素，因此 `vl << 2` 就是本批字节数。`vslideup.vi` 把上一批最后一个 ciphertext（首批为 IV）放到反馈向量开头，再接本批除最后一块之外的 ciphertext；`vslidedown.vx` 在明文覆盖输入前保存本批最后 ciphertext，供下一批使用。AES-128/192/256 的 key-size 分派被移到主循环外，round key 只装一次；尾部不足一个满 VLEN 批次时只降低 VL，不另复制一套 scalar 尾循环。

```text
feedback = [previous_ciphertext, C0, C1, ... C(n-2)]
plaintext = AES_DEC([C0, C1, ... C(n-1)]) XOR feedback
next_previous = C(n-1)      // store plaintext 前由 vslidedown.vx 保存
```

**最有价值的实验、源码与 benchmark 细节：** QEMU 在 VLEN=128/256/512/1024 下各跑 157,167 项 AES-128/192/256 检查，覆盖 known-answer、随机输入、padding、chunk、重叠 buffer 与状态更新；四种 VLEN 的 digest 一致，软件控制组也一致，并确认 intrinsic 实际启用。SpacemiT X100 2.2GHz、VLEN=256、Linux 6.18.3 上，JMH 使用 5×1s warmup、8×1s measurement、2 forks、单线程、512MB pretouch，并用 perf 采 cycles/instructions。64B 起吞吐提升 1.1772–1.2191×；256B 为 1.3420–1.3837×；1KiB 为 1.5291–1.5940×；16KiB 为 1.6322–1.6772×。代价也没有隐藏：16B 的 AES-128 从 9.2270 降到 8.6483 Mops/s（0.9373×），三种 key 的置信区间重叠，作者判断固定 setup 占主导，因此没有再加 16B 专用快路。生成 stub 反而从 744B 缩到 564B。perf 事件统计的是完整 benchmark operation，不只是 stub，不能把 instructions/op 直接当成汇编循环指令条数。

**适合的工程师背景：** 熟悉 HotSpot stub generator、RISC-V Vector/AES 扩展、CBC 数据依赖，或正在把定宽 SIMD 循环改造成可伸缩向量实现的运行时工程师。

**预计阅读收益：** 约 50–70 分钟；能掌握可伸缩向量的批次设计、in-place CBC 反馈保存、短消息控制组与代码尺寸权衡，并得到一套可迁移到其他 crypto intrinsic 的验证矩阵。

## 02 · Kotlin/Wasm：把 `KClass` 构造移出内联 checked-cast 失败路径

**原文与日期：** JetBrains Kotlin/Wasm 团队，2026-11-02 20:18（中原标准时间）；[Kotlin PR #9461](https://github.com/JetBrains/kotlin/pull/9461)、[KT-91118](https://youtrack.jetbrains.com/issue/KT-91118) 与 [3 个文件的源码 diff](https://github.com/JetBrains/kotlin/pull/9461/files)。

**为什么值得读：** checked cast 的成功路径很短，但旧 lowering 会在每个潜在失败点内联构造目标 `KClass` 所需的 TypeInfoData 与名字字符串；大量重复 cast site 会把“极少执行的异常路径”膨胀进生产 Wasm。补丁没有改变 fast path，而是重新组织失败路径的归属：普通 class 传 RTTI 给共享 stdlib helper，interface 和 external class 则按目标类型与 nullable 位生成每文件 helper，再交给 Binaryen 跨文件合并。

**核心技术结论：** 对非 interface、非 external class，lowering 调用 `THROW_CCE_WITH_RTTI(value, wasmGetTypeRtti<T>(), isNullable)`，`KClassImpl` 只在共享抛错函数中构造。对 interface/external 类型，`getKClass<T>()` 的信息仍必须保留，因此以 `(IrClassSymbol, isNullable)` 为 key 缓存 `throwCce$N$<T>`；同文件相同目标只生成一次，Binaryen 再做跨文件 identical-function merging。所有 helper 在一个 `stageController.restrictTo(anchor)` 作用域内创建，以获得稳定且互异的 incremental compilation signature。

```kotlin
if (!klass.isInterface && !klass.isEffectivelyExternal()) {
    return irCall(symbols.throwTypeCastWithRttiException).also {
        it.arguments[0] = value
        it.arguments[1] = irCall(symbols.wasmGetTypeRtti)
        it.arguments[2] = irBoolean(isNullable)
    }
}
val helper = cceHelpers.getOrPut(klass.symbol to isNullable) {
    createCceHelper(klass, isNullable)
}
```

**最有价值的实验、源码与 benchmark 细节：** 生产模式经过 Binaryen 后，相对 master 的 Compose benchmark 包体积下降 3.45%，KotlinConf 下降 4.15%。diff 只有 3 个文件、+60/-9：新增 compiler symbol、重写 `WasmTypeOperatorLowering`，并在 stdlib 增加 RTTI 共享失败函数；quality gate dry-run 成功。这里测量的是最终 Wasm 产物大小，不是运行时吞吐，不能据此声称 cast 更快。反而最值得迁移的是证据链：先证明膨胀来自冷失败路径的重复 TypeInfo/KClass 物化，再在 IR、stdlib 与 Binaryen 三层分工去重，同时保留 interface/external 的语义差异。

**适合的工程师背景：** 熟悉 Kotlin IR lowering、Kotlin/Wasm RTTI/KClass、Binaryen，或在 AOT 编译器中治理异常路径和泛型/反射元数据膨胀的工程师。

**预计阅读收益：** 约 35–50 分钟；能学会如何在不触碰热成功路径的前提下缩小冷代码，以及如何为增量编译稳定性设计生成 helper 的作用域和命名。

## 03 · Rust：`cargo check` 不需要为不会 codegen 的 MIR 计算 reachable set

**原文与日期：** rustc 贡献者，2026-11-07 22:33（中原标准时间）；[rust-lang/rust PR #165602](https://github.com/rust-lang/rust/pull/165602)、[rustc-perf 对比](https://perf.rust-lang.org/compare.html?start=e30d778f3029b78bb9c2e0dbe11a3b7389b652c4&end=49567479eba3f5e0a0ea9b94401873b264f00688&stat=instructions:u) 与 [`encoder.rs` diff](https://github.com/rust-lang/rust/pull/165602/files)。

**为什么值得读：** `reachable_set` 用于判断哪些 generic/inline item 的 optimized MIR 必须写入 crate metadata，供下游 codegen 使用；但 `cargo check` 没有代码生成，照样先跑这项全 crate 查询，再在 metadata encoder 中不写对应 MIR。补丁把产物需求前移成查询门控：不是让 `reachable_set` 本身快一点，而是证明这个构建模式根本不该问它。

**核心技术结论：** `should_encode_mir` 的参数从 `&LocalDefIdSet` 改为 `Option<&LocalDefIdSet>`；仅当 `output_types.should_codegen()` 时计算并传入 `Some`，check 路径传 `None`。review 指出 `None` 的语义容易被误读成“缺少可选精确信息”，作者随后补文档与断言，明确 `reachable_set.is_some() == should_codegen()`；因此 `None` 代表“这个 session 不会 codegen，针对 LLVM 的 MIR 一律无需编码”，而不是保守回退。

```rust
let reachable_set = tcx.sess.opts.output_types.should_codegen()
    .then(|| tcx.reachable_set(()));
assert_eq!(reachable_set.is_some(), tcx.sess.opts.output_types.should_codegen());

should_encode_mir(tcx, reachable_set, def_id)
```

**最有价值的实验、源码与 benchmark 细节：** rustc-perf 以 userspace instructions 作为主判据：primary 33 个改善，平均 -0.8%，范围 -5.5% 到 -0.2%，0 个回退；secondary 11 个改善，平均 -0.4%，范围 -0.7% 到 -0.2%，同样 0 个回退。Primary Max RSS 有 3 个改善，平均 -2.5%（-4.5% 到 -1.0%）。cycles 较噪：primary 2 个改善平均 -5.1%，secondary 3 个回退平均 +2.3%，因此不应拿 cycles 作为主结论。Bootstrap 484.651s → 483.527s（-0.23%），artifact 406.22 → 406.21MiB（约 0%）。实现只改 `compiler/rustc_metadata/src/rmeta/encoder.rs`，核心是少发起一次昂贵查询；性能收益主要落在 check 场景，完整 codegen 仍需原 reachable set 以保持下游单态化/内联所需 MIR。

**适合的工程师背景：** 熟悉 rustc query system、crate metadata、MIR 编码，或维护具有 check/analyze/build 多种产物模式的编译器工程师。

**预计阅读收益：** 约 30–45 分钟；能掌握如何从“后面不用结果”反推查询门控位置，并用主指标、噪声指标、内存与 bootstrap 四组数据约束结论。

## 本期结论

三篇材料都在删除“语义上已经知道却仍重复支付”的工作：宽向量仍按单 block 跑、冷异常路径在每个 cast site 重建 `KClass`、无 codegen 的构建仍计算 codegen 才需要的 reachable set。真正可迁移的方法不是简单删代码，而是先写清不可破坏的边界——CBC 反馈与 in-place 覆盖、interface/external RTTI 语义、下游 codegen 所需 MIR——再用针对性控制组证明优化只作用在目标路径。
