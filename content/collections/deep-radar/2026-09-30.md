## 01 · JVM：给“不存在的 CLDR 数据”也建立缓存

**原文与日期：** Naoto Sato，2026-09-30 06:50（中原标准时间）；[OpenJDK PR #33133](https://github.com/openjdk/jdk/pull/33133)、[完整源码 patch](https://github.com/openjdk/jdk/pull/33133/files) 与 [JDK-8392996](https://bugs.openjdk.org/browse/JDK-8392996)。

**为什么值得读：** 这是 negative caching 的一个极小但完整的生产案例。时区名称格式化会查询 `metazone.dstoffset.<TZID>`；大多数时区没有显式 DST offset，旧路径每次都重新选择 CLDR provider、规范化时区 ID、构造资源 key，再做一次注定返回 `null` 的查找。普通缓存若只能保存非空结果，对最常见的“缺失”状态反而完全无效。

**核心技术结论：** 补丁在 `TimeZoneNameUtility` 增加 `ConcurrentHashMap<String, String>`，以原始 TZID 为键。`computeIfAbsent` 只在首次查询时访问 `LocaleResources`；真实值原样保存，不存在则保存空字符串哨兵。对调用者返回时再把空串翻译回 `null`，因此外部语义不变，但“没有数据”从重复 I/O/资源树遍历变成一次计算后的稳定状态。

```java
private static final Map<String, String> cachedExplicitDstOffsets =
    new ConcurrentHashMap<>();

var dstOffset = cachedExplicitDstOffsets.computeIfAbsent(tzid, key -> {
    var value = localeResources.getTimeZoneNames(
        "metazone.dstoffset." + canonicalTZID(key).orElse(key));
    return value == null ? "" : value;
});
return dstOffset.isEmpty() ? null : dstOffset;
```

**最有价值的实验、源码与 benchmark 细节：** 作者在 macOS 上复测 JBS 中的格式化用例。New York 从 `303.9 B/op, 191.7 ns/op` 降到 `32.0 B/op, 90.6 ns/op`：分配下降 `89.47%`，耗时下降 `52.74%`，约 `2.12×`。Vancouver 从 `240.0 B/op, 216.8 ns/op` 降到 `88.0 B/op, 118.4 ns/op`：分配下降 `63.33%`，耗时下降 `45.39%`，约 `1.83×`。

源码证据只有 15 行新增、5 行删除，关键不在容器本身，而在空值表示：`ConcurrentHashMap` 不能保存 `null`，若直接返回 `null`，`computeIfAbsent` 下一次仍会重新计算；空字符串哨兵才让缺失结果真正进入缓存。边界同样要保留：公开结果只有一台 Mac、两个时区和单组数据，没有置信区间、冷启动成本或缓存增长压力；PR 仍是 draft。

**适合的工程师背景：** 维护 JDK locale/time-zone、资源包缓存，或正在排查“查不到却反复查”的配置、DNS、schema 与 metadata 热路径的 Java/JVM 工程师。

**预计阅读收益：** 约 20–30 分钟；能学到如何在不改变 `null` API 契约的前提下缓存缺失状态，并用 `B/op` 与 `ns/op` 同时验证查找链和分配链是否真正被截断。

## 02 · Rust：让路径构造 API 从类型上拒绝临时 `Vec`

**原文与日期：** Rust compiler 团队，2026-09-29 20:47（中原标准时间）；[Rust PR #163485](https://github.com/rust-lang/rust/pull/163485)、[完整源码 patch](https://github.com/rust-lang/rust/pull/163485/files) 与 [rustc-perf 对比](https://perf.rust-lang.org/compare.html?start=b46c90c5619a16a0c7e4d0f4e9e1ad4db4cf106e&end=0bcf40dc0c6b1a2253f428ebaa94e0e54aa98617&stat=instructions:u)。

**为什么值得读：** builtin macro 扩展器大量构造短路径，例如 `$crate::option::Option::Some`。旧 API 的 `std_path(&[Symbol]) -> Vec<Ident>` 与 `path(..., Vec<Ident>)` 迫使每次调用先创建堆 `Vec`，随后又把元素搬到 AST 的 `ThinVec<PathSegment>`。补丁不靠调用者自律，而是重塑 API：数组、切片和标准库符号数组直接实现 `ToPath`，把“临时收集再转换”从合法的默认写法中移除。

**核心技术结论：** 新的 `StdPath<const N: usize>([Symbol; N])` 保留编译期长度，`ToPath` 分别为 `StdPath<N>`、`[Ident; N]` 与 `&[Ident]` 生成最终 `Path`。调用点从 `vec![...]` 或 `&[...] -> Vec` 改成固定数组；标准库路径直接预留 `N + 1` 个 `PathSegment`，一次填入 `$crate` 与其余段。补丁同时抽出 `expr_call_intrinsic`、`item_fn`、`pat_ident_sym` 等 helper，减少重复 AST 样板。

```rust
pub struct StdPath<const N: usize>(pub [Symbol; N]);

pub fn std_path<const N: usize>(&self, components: [Symbol; N]) -> StdPath<N> {
    StdPath(components)
}

pub fn path(&self, span: Span, components: impl ToPath) -> Path {
    self.path_all(span, components, vec![])
}

let some = cx.std_path([sym::option, sym::Option, sym::Some]);
```

**最有价值的实验、源码与 benchmark 细节：** 完整改动覆盖 27 个文件，新增 260 行、删除 291 行。rustc-perf 的可靠指标 `instructions:u` 没有显著 primary 变化；7 个 secondary 改善样本平均 `-0.2%`，范围 `-0.3%..-0.2%`，没有显著指令数回退。bootstrap 从 `491.711 s` 到 `491.207 s`，下降 `0.10%`；artifact 体积基本不变。

负向数据更值得看：最大 RSS 有 1 个 primary 样本回退 `+2.2%`，3 个 secondary 回退平均 `+3.6%`（`+3.4%..+3.8%`）；也有 primary `-0.9%` 和 secondary `-2.3%` 的改善样本。cycles 没有相关结果。因此最稳妥的结论只是“短路径构造的 API 与分配模型更直接，并在少量次级样本中减少指令”，不能外推为 rustc 全局 wall-clock 或内存改善。

**适合的工程师背景：** 熟悉 rustc AST expansion、derive/builtin macro，或正在设计高频 builder API、希望用 const generics 与 trait 把临时分配从接口层消掉的编译器/基础库工程师。

**预计阅读收益：** 约 30–45 分钟；能学到如何把性能约束编码进 API 类型，而不是靠 code review 逐个发现 `vec![]`，以及如何在微小正向指标旁保留 RSS 回退和统计显著性边界。

## 本期结论

两篇材料共同说明：最容易被忽略的成本往往藏在“没有结果”和“只用一下”的对象里。CLDR 补丁让缺失资源成为可缓存状态，在两个时区样本中把耗时降低 45.39%–52.74%；rustc 补丁让固定长度路径直接流入最终 AST 容器，避免短命 `Vec`，但公开可靠收益只有次级样本平均 0.2%，RSS 还出现最高 3.8% 的显著回退。前者是明确的热路径修复，后者更像值得复用的 API 设计实验；两者都不应越过当前单机、样本与评审状态的边界。
