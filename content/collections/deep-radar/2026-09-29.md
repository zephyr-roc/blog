## 01 · JVM：让空的 Shenandoah `HdrSeq` 不再预付 56 槽数组

**原文与日期：** pf0n，2026-09-29 08:04（中原标准时间）；[OpenJDK PR #33110](https://github.com/openjdk/jdk/pull/33110)、[完整源码 patch](https://github.com/openjdk/jdk/pull/33110/files) 与 [JDK-8393152](https://bugs.openjdk.org/browse/JDK-8393152)。

**为什么值得读：** 这是一个很干净的“对象存在不等于存储必须存在”案例。`ShenandoahPhaseTimings` 会持有许多 `HdrSeq`，旧构造函数为每个实例立刻分配 `MagBuckets = 56` 个指针并全部清零，即使该阶段从未记录过样本。补丁把直方图的逻辑状态与物理存储拆开：空序列只保留 `_hdr == nullptr`，直到第一次 `add()` 才物化数组。这个模式可迁移到运行时统计、诊断计数器和稀疏 profiling 数据结构。

**核心技术结论：** 构造函数只初始化空指针和最小值；`allocate_hdr()` 由 `add(double)` 与非空 `add(const HdrSeq&)` 调用。析构、`clear()` 和合并路径都显式接受“从未分配”的状态。由于 `percentile()` 过去默认 `_hdr` 存在，补丁同时为 `num() == 0` 增加早退；`NONCOPYABLE(HdrSeq)` 则阻止延迟分配后出现浅拷贝所有权错误。

```cpp
HdrSeq::HdrSeq() :
  _hdr(nullptr),
  _minimum(DBL_MAX) {}

void HdrSeq::allocate_hdr() {
  if (_hdr == nullptr) {
    _hdr = NEW_C_HEAP_ARRAY(int*, MagBuckets, mtGC);
    for (int c = 0; c < MagBuckets; c++) _hdr[c] = nullptr;
  }
}

void HdrSeq::add(double val) {
  allocate_hdr();
  // 原有分桶逻辑
}
```

**最有价值的实验、源码与 benchmark 细节：** 作者给出的 Native Memory Tracking 分配栈显示，修改前 `HdrSeq::HdrSeq()` 路径在峰值累计 `131,712 B`、294 次分配；修改后只有真正接收样本的 `HdrSeq::add()` 路径累计 `35,840 B`、80 次分配。净减少 `95,872 B`，按公开数字计算下降 `72.79%`，占用约缩小为原来的 `1/3.67`。这不是吞吐 benchmark，而是对目标成本更直接的分配栈证据：少掉的是空直方图的预分配，不应推断为 GC pause 或应用吞吐同比改善。

补丁还新增 `empty_hdr` gtest，逐个检查空序列 `0..100` 百分位均返回 0、`clear()` 不触发分配、空序列合并仍保持空；同时把 `_card_stats[i]` 的释放从 `delete` 修正为 `delete[]`。后者是独立的数组释放正确性修复，不应计入上述 95,872 B 收益。当前实验边界同样重要：公开数据只有单组 NMT 峰值，没有多 workload、wall-clock 或 RSS 置信区间，而且 PR 仍是 draft。

**适合的工程师背景：** 熟悉 HotSpot C-heap/NMT、Shenandoah phase timing，或正在设计大量“通常为空、偶尔写入”的运行时统计对象的 JVM 与系统工程师。

**预计阅读收益：** 约 20–30 分钟；能学到如何把延迟物化完整地传播到构造、析构、查询、清理与合并路径，并用分配栈而非笼统 RSS 验证小型基础数据结构的收益。

## 本期结论

`HdrSeq` 补丁的价值不在于 94 KiB 本身，而在于把统计对象的“逻辑空状态”做成真正零附加存储，并为所有读取和生命周期路径补齐这一状态。公开 NMT 数据显示峰值从 `131,712 B` 降到 `35,840 B`，但它仍只有单组内存证据、没有延迟或吞吐结果；在更多 workload 与评审完成前，最稳妥的结论是“空直方图成本显著下降”，而不是 Shenandoah 整体性能提升。
