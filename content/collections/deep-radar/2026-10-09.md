## 01 · OpenJDK：把 Curve448 的 limb 数量减半，代价是显式管理 112 位乘积

**原文与日期：** Sean M. Emery（smemery），2026-10-09 07:17（中原标准时间）；[OpenJDK PR #33277](https://github.com/openjdk/jdk/pull/33277)、[完整源码 diff](https://github.com/openjdk/jdk/pull/33277/files) 与 [JBS JDK-8393160](https://bugs.openjdk.org/browse/JDK-8393160)。

**为什么值得读：** Curve448 的域元素是 448 位整数。旧实现把它切成 16 个 28-bit limb，方便让中间乘积留在 64 位范围内，但每次乘法、平方、进位与归约都要处理更多数组槽和交叉项。这个 patch 改成 8 个 56-bit limb，直接把表示层的循环宽度减半；为了不让 56×56-bit 乘积溢出 `long`，又把每项乘积显式拆成低 56 位和高位。它是一个很干净的案例：数据布局优化只有和机器整数宽度、模数结构及正确归约一起看，才有意义。

**核心技术结论：** 新的 `IntegerPolynomial448` 固定 `BITS_PER_LIMB = 56`、`NUM_LIMBS = 8`，乘法和平方都以 `Math.multiplyHigh` 取得 128 位乘积的高半部，再与普通乘法结果的右移部分拼成高位 digit。低位用 56-bit mask 截断：

```java
long d0 = aa0 * bb0;
long dd0 = Math.multiplyHigh(aa0, bb0) << 8 | (d0 >>> 56);
d0 &= LIMB_MASK;
```

Curve448 的素数是 `p = 2^448 - 2^224 - 1`，因此 `2^448 ≡ 2^224 + 1 (mod p)`。16 个乘积列不必做通用大整数除法：高半列可同时折回低 224 位和高 224 位。源码中的 `r[0] = c0 + c8 + c12`、`r[4] = c4 + c8 + (c12 << 1)` 正是在展开这一同余关系，之后再统一传播 carry。原先由 `FieldGen` 生成的 16×28-bit 特例被移除，新的 928 行实现把乘法、平方、整数乘法和归约路径放在同一类中，便于逐项审查边界。

**最有价值的实验、源码与 benchmark 细节：** 作者报告 AArch64、纯 Java 路径下，密钥对生成提升 `45%`、密钥协商提升 `46%`、Ed448 签名提升 `45%`、Ed448 验证提升 `47%`。改动只涉及两个文件：生成器删除 37 行旧 Curve448 参数与 carry/reduce 序列；`IntegerPolynomial448.java` 新增 928 行手写 8-limb 算术。乘法不依赖 BigInteger，也没有 JNI 往返，因此四项收益能直接指向域算术热路径，而不是 provider 切换。

证据边界同样重要：PR 文本只给相对百分比，没有 JMH 命令、绝对吞吐、方差、CPU 型号或 x86_64 数据；而且尚无正式 Reviewer。`Math.multiplyHigh` 在不同后端能否稳定落成高半乘指令、手写展开是否增加 code cache 压力，都应在合入前用目标架构的汇编与完整加密基准复测。这里足以确认“源码机制与 AArch64 定向收益一致”，不足以声称所有平台都快 45%。

**适合的工程师背景：** 熟悉 Java 密码学 provider、有限域、HotSpot 整数 intrinsic 或多精度算术，想理解 64 位 limb 如何借伪梅森素数完成快速归约的工程师。

**预计阅读收益：** 约 40–55 分钟；能掌握 limb 宽度与交叉乘积数量的权衡、如何用 `multiplyHigh` 表示 56×56-bit 结果，以及怎样把 `2^448 ≡ 2^224 + 1` 落成固定索引的 carry/reduce 代码。

## 02 · rustc：六个小早退把 Diesel 的新求解器开销从 1.49×压到 1.31×，但全局均值接近零

**原文与日期：** Nicholas Nethercote（nnethercote），2026-10-08 18:27（中原标准时间）；[Rust PR #163981](https://github.com/rust-lang/rust/pull/163981)、[完整源码 diff](https://github.com/rust-lang/rust/pull/163981/files) 与 [官方 rustc-perf 比较](https://perf.rust-lang.org/compare.html?start=fc2324d0546aa6782c45b76247266a0c37db0b8a&end=72d027b9aaffb1bdcbbb7a99d0fa20cbfe294b2c&stat=instructions%3Au)。

**为什么值得读：** 这不是一次“换算法就全面变快”的故事，而是 profile 指向的六个小浪费：空结构用 `extend` 重建、相同 query value 仍进入关系求解、失败候选仍创建空 usage、循环内重复解析 lang item，以及常见类型没有预驻留。它展示了 trait solver 这类高度递归、分配密集系统中，怎样把不可见的固定开销逐层移出热路径；更难得的是官方 perf 结果没有被定向 Diesel 大幅收益掩盖。

**核心技术结论：** 最直接的早退发生在 `unify_query_var_values`：原值与响应值相等时，不再构造 `ResponseRelating` 并沿调用链重复做等价检查。

```rust
for (&orig, response) in iter::zip(original_values, var_values.var_values.iter()) {
    if orig == response {
        continue;
    }
    ResponseRelating::new(&**delegate, span).relate(orig, response).unwrap();
}
```

其余提交把 canonicalizer 的三个集合从逐项 `extend` 改成 `clone_from`，将 `goal_lang_item` 从 `fast_reject_assumption` 的循环元素级调用外提到循环级，令 `Err(NoSolution)` 跳过 `CandidateHeadUsages::default()` 与无效 `merge_usages`，并增加 type var、匿名 bound type 与 root-universe placeholder 的预驻留。共同原则不是特殊处理 Diesel，而是减少新求解器在高重复度 goal/candidate 上的构造、哈希与递归入口。

**最有价值的实验、源码与 benchmark 细节：** 作者的本地 instruction-count 对照为：旧求解器 `37.9B`，原始新求解器 `56.4B`（旧版的 `1.49×`），应用本 PR 后 `49.5B`（`1.31×`）。也就是相对原始新求解器减少 `6.9B` 指令、约 `12.2%`，与旧求解器的差距从约 `48.8%` 收窄到 `30.6%`。

官方 rustc-perf 的全局视角明显更克制：primary instruction-count 的 15 个显著样本合计均值为 `0.0%`，其中 6 个回退平均 `+0.4%`、9 个改善平均 `-0.2%`；secondary 有 55 个改善，平均 `-1.1%`、最佳 `-11.1%`，同时 3 个回退平均 `+0.3%`。Max RSS 汇总为 primary `-2.7%`、secondary `+2.6%`；cycles 则是 primary `+2.4%`、secondary `-1.1%`。bootstrap `484.956 → 485.101 s`、artifact `406.45 → 406.59 MiB`，都回退 `0.03%`。

作者把极短的 `helloworld` 等回退归因于启动时预驻留更多值，并认为可换取 Diesel 与若干新求解器样本的绿色结果；项目仍正确保留 `perf-regression` 标签。可迁移的结论是：热路径优化应同时报告定向 workload、全局 instruction count、cycles、RSS 与启动成本，不能只拿最大改善作标题。

**适合的工程师背景：** 熟悉 Rust trait solving、rustc query/canonicalization、profile-guided compiler optimization，或正在为分配密集型递归算法寻找早退与循环不变量的工程师。

**预计阅读收益：** 约 35–50 分钟；能看到六类微优化如何叠加成 6.9B 指令差异，并学会用 rustc-perf 的 primary/secondary、instructions/cycles/RSS 多口径反驳“单一大样本等于全局收益”。

## 本期结论

两篇材料共同说明，“减少工作量”必须落到实际热路径而不是抽象复杂度。Curve448 把 limb 数量减半，再用高半乘法和模数同余关系守住正确性，得到四项 45%–47% 的 AArch64 定向收益；rustc 则用六个早退、复用与预驻留把 Diesel 的新求解器指令数减少约 12.2%，但全局 primary 指令均值仍是 0.0%，cycles 还有回退。最值得迁移的方法是：源码机制、定向实验与全局反证必须同时出现，任何一层缺失都不应写成普遍结论。
