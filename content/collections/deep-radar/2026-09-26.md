## 01 · Rust/Tokio：单分隔符走 `memchr`，多分隔符改为 O(1) 字节查表

**原文与日期：** Emmanuel Bartlett，2026-09-25 21:33（中原标准时间）；[Tokio PR #8512](https://github.com/tokio-rs/tokio/pull/8512)、[完整源码 patch](https://github.com/tokio-rs/tokio/pull/8512/files) 与 [`AnyDelimiterCodec` 源码](https://github.com/tokio-rs/tokio/blob/master/tokio-util/src/codec/any_delimiter_codec.rs)。

**为什么值得读：** 旧实现对输入中的每个字节调用 `seek_delimiters.contains(b)`。当分隔符集合有 `k` 个元素时，扫描 8 MiB 输入不仅要读完整 haystack，还会在热循环中做最多 `k` 次线性比较。补丁没有改变 frame、`max_length` 或丢弃状态机，而是按分隔符数量特化：恰好一个分隔符时复用 `LinesCodec` 已采用的 `memchr`；多个或零个分隔符时，在构造阶段建立按 byte 值索引的 256 项布尔表。

**核心技术结论：** 这是一个很干净的“把集合成员测试移出热循环”案例。单值搜索交给 libc/平台优化的 `memchr`，多值搜索则把 `Vec::contains` 的 O(k) 比较降为一次索引读取。代价是每个 codec 实例增加 256 bytes；作者也试过 32-byte 的 `u64` bitset，但小 frame 更慢，因此保留直接查表。工程上不能只比较大 buffer 峰值，还要同时检查小 frame 与对象体积。

```rust
let haystack = &buf[self.next_index..read_to];
let new_chunk_offset = match self.seek_delimiters[..] {
    [delimiter] => crate::util::memchr::memchr(delimiter, haystack),
    _ => haystack
        .iter()
        .position(|&b| self.delimiter_table[b as usize]),
};
```

**最有价值的实验、源码与 benchmark 细节：** 在 Ryzen 9 5900X 上扫描 8 MiB 输入：单分隔符、1 KiB frame 从 `1.77` 提升到 `3.37 GB/s`，吞吐增加 90.4%，即 1.90 倍；四分隔符、256 B frame 从 `0.67` 提升到 `1.51 GB/s`，增加 125.4%，即 2.25 倍。2–4 byte 小 frame 保持不变，说明扫描成本不再占主导时没有可见收益。新增测试覆盖单分隔符、空分隔符、高位字节 `0x80/0xff`、最大长度和 Debug 输出；手写 `Debug` 刻意隐藏派生缓存，维持公开格式。

证据边界也很明确：数字只有一台 Zen 3 机器、单次作者报告，没有 Criterion 原始分布、不同 libc/架构或 codec 构造频率数据；256-byte 增量在大量短生命周期 codec 场景可能影响 cache footprint。复测应把分隔符数量、命中位置、frame 长度、构造/复用比例与 x86/AArch64 分开扫描。

**适合的工程师背景：** 维护网络协议解析、Tokio codec、字节扫描器，或需要在 SIMD/libc primitive、查表和 bitset 之间做热路径权衡的 Rust 工程师。

**预计阅读收益：** 约 25–40 分钟；能掌握按 cardinality 特化搜索、把派生索引放到构造阶段，以及同时审视吞吐、对象尺寸与小输入边界的方法。

## 02 · Kotlin/Wasm：一个 checked cast 为什么会把异常 helper 带进所有程序

**原文与日期：** Kotlin/Wasm 团队，2026-09-25 16:33（中原标准时间）；[Kotlin PR #8425](https://github.com/JetBrains/kotlin/pull/8425)、[完整源码 patch](https://github.com/JetBrains/kotlin/pull/8425/files) 与 [Wasm stdlib 运行时代码](https://github.com/JetBrains/kotlin/tree/master/libraries/stdlib/wasm)。

**为什么值得读：** `getKotlinException` 是 JS 互操作的 DCE root。旧代码从 JS error 取回 `kotlinException` 后直接收窄成 `Throwable`；小整数/布尔装箱 helper 也把编译器 intrinsic 的泛型返回值再次收窄。虽然这些路径在源码里很短，checked cast 会引用带详细信息的 `THROW_CCE_WITH_INFO`，于是任何最小程序都无法把整套异常 helper 消掉。这篇补丁把“产物为什么凭空多出十几 KB”追到类型收窄和 DCE 可达图，而不是只压缩生成文本。

**核心技术结论：** JS 侧属性并不保证真是 `Throwable`，因此恢复异常时应先以 `JsReference<Any>?` 接收，再用安全转换；失败就包装为 `JsException`。装箱 intrinsic 的调用者只把结果存为 `Any?`，返回类型也改为 `Any?`，避免为一个并不需要的静态窄类型生成运行时检查。两处修改都削掉了从 DCE root 到 CCE helper 的边。

```kotlin
val kotlinException: JsReference<Any>? = (v as? JsError)?.kotlinException
return kotlinException?.get() as? Throwable ?: JsException(v)

internal fun <T> createBoxIntrinsic(x: T): Any? =
    TODO("Make intrinsic after bootstap")
```

**最有价值的实验、源码与 benchmark 细节：** 六组 size test 的 DCE Wasm 分别从 `33,556→28,061`、`33,881→28,391`、`33,955→28,463`、`38,783→33,360`、`33,613→28,117`、`34,473→28,957 bytes`，缩小 13.98%–16.38%。对应 `.mjs` 大多减少约 351–399 bytes。`helloWorldPromise.kt` 的 `wasm-opt` 输出从 `3,562` 降至 `1,769 bytes`，缩小 50.34%；其余极小 `wasm-opt` 样本只变化 0–3 bytes，说明收益取决于被整块裁掉的 helper 是否仍有其他引用。

补丁同时加入 JS→Kotlin 异常回归：真正的 Kotlin exception 必须保留对象身份，伪造的 `kotlinException` 属性若指向非 `Throwable`，必须回退成 `JsException`。限制在于这里测的是静态大小而非下载、解析或启动时间；PR 仍在开放评审，且另一项并行改动正在把装箱 intrinsic 返回类型改为非空 `Any`。工程复测应同时比较 gzip/Brotli 后大小和浏览器实例化时间。

**适合的工程师背景：** 熟悉 Kotlin/Wasm、JS interop、IR/DCE 或正在追踪“一个类型检查为何让最小 Wasm 包膨胀”的编译器与前端基础设施工程师。

**预计阅读收益：** 约 30–45 分钟；能理解 DCE root、运行时 helper 可达性、checked cast 与安全转换的代码尺寸差异，以及如何用 size test 固化最小产物预算。

## 本期结论

两项改动都在处理“隐藏在抽象背后的固定成本”。Tokio 把每字节的线性集合搜索变成 `memchr` 或一次查表，在长扫描上达到 1.90–2.25 倍吞吐；Kotlin/Wasm 则去掉 DCE root 上不必要的类型收窄，让完整异常 helper 从最小程序的可达图中消失，DCE Wasm 缩小约 13%–16%。前者提醒先按集合基数选择 primitive，后者提醒静态类型的便利可能转化为运行时依赖。
