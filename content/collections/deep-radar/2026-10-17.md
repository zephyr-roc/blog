## 01 · OpenJDK s390：普通与 ZGC 数组复制改走向量循环

**原文与日期：** Harshit470250，2026-10-16 16:45（中原标准时间）；[OpenJDK PR #33403](https://github.com/openjdk/jdk/pull/33403)、[完整源码 diff](https://github.com/openjdk/jdk/pull/33403/files) 与 [JBS 8393875](https://bugs.openjdk.org/browse/JDK-8393875)。

**为什么值得读：** 这不是把标量 load/store 机械替换成一条向量指令。普通 conjoint copy 需要处理重叠区间和反向复制；ZGC 路径还要检查 load-bad、store-bad 与 store-good 颜色位，并在屏障不能走快路径时回退。补丁把“批量复制”和“屏障语义”一起编码进 s390 stub，展示了 GC barrier 与 ISA 向量化真正交汇的工程边界。

**核心技术结论：** 普通 conjoint stub 原本每轮复制 8 字节，现在每轮以 `VL/VST` 各处理两个 16 字节向量，即 32 字节，并保留标量尾部。ZGC disjoint/conjoint stub 则每次载入两个 oop（16 字节），用向量 AND 与 `VTM` 一次检查颜色掩码；load-good/store-good 时整向量清色、着色并写回，检测到坏位才拆成两个 64 位 lane 调用既有标量屏障。普通 disjoint copy 继续使用更合适的 `MVC`，没有为了“全向量化”替换已经更快的路径。

```cpp
__ z_vl(Vdata, Address(src));
__ z_vn(Vscratch, Vdata, _vec_load_bad);
__ z_vtm(Vscratch, Vscratch);
__ branch_optimized(Assembler::bcondNotZero, fallback);
__ z_vo(Vdata, Vdata, _vec_store_good);
__ z_vst(Vdata, Address(dst));
```

**最有价值的实验、源码与 benchmark 细节：** PR 给出了 15 次采样的 `ArrayCopyObject` JMH 吞吐。普通 conjoint copy 在规模扩大后收益稳定上升：

| 元素数 | 修改前 ops/ms | 修改后 ops/ms | 实算变化 |
| ---: | ---: | ---: | ---: |
| 31 | 74,059.126 | 92,964.735 | +25.53% |
| 127 | 31,167.686 | 53,721.584 | +72.36% |
| 2,047 | 2,301.107 | 4,755.938 | 2.07× |
| 8,191 | 582.822 | 1,223.752 | 2.10× |

ZGC 路径更能说明限制：conjoint 31 元素从 45,696.006 降至 36,914.687 ops/ms，回退 19.22%；63 元素基本持平（+0.64%），127 元素起转正，2,047–8,191 元素提升约 20.56%–26.28%。ZGC disjoint 六档全部改善，范围约 10.04%–27.02%。这说明向量屏障的固定 mask 装载和 fallback 组织会伤害极小数组，但大数组能用一次判断覆盖两个 oop，逐步摊薄成本。

**适合的工程师背景：** 熟悉 HotSpot stub generator、ZGC 着色指针与 load/store barrier，或需要在非 x86 ISA 上优化运行时内存原语的工程师。

**预计阅读收益：** 约 40–60 分钟；能理解重叠数组反向复制、向量化屏障检查、标量 tail/fallback 如何组合，并学会为什么必须按大小与 GC 路径拆分 benchmark。

## 02 · OpenJDK JDI：把 7 万类全局扫描收缩到目标 class loader

**原文与日期：** benshuai5D，2026-10-16 23:13（中原标准时间）；[OpenJDK PR #33414](https://github.com/openjdk/jdk/pull/33414)、[完整源码 diff](https://github.com/openjdk/jdk/pull/33414/files) 与 [JBS 8343851](https://bugs.openjdk.org/browse/JDK-8343851)。

**为什么值得读：** JDI 为引用数组执行 `ArrayType.newInstance()` 时，需要从数组签名找到组件类。旧实现调用 JVMTI `GetLoadedClasses`，遍历整个 VM 的已加载类，并为每个候选读取签名；应用加载的类越多，调试器一次数组分配就越接近 O(全局类数)。补丁没有增加缓存或改变协议，而是利用 JVM 5.3.3 的类加载器不变量，先把搜索空间限制在定义该数组的 loader 内，属于很容易迁移到调试器、反射和元数据索引的“先按所有权分区，再全局兜底”优化。

**核心技术结论：** `getComponentClass()` 先取得 array class loader，调用 `GetClassLoaderClasses` 只遍历该 loader 可见的类；公共的 `findComponentClass()` 负责签名与 defining loader 双重判等。如果局部集合未命中，再回退原有 `GetLoadedClasses` 全局扫描。hidden class 的签名包含 `.`，且 hidden class 及其数组不会出现在 `GetClassLoaderClasses` 中，因此这类签名直接跳过局部路径，保留全局查找；primitive 多维数组与 hidden array 也新增回归测试。

```c
if (strchr(componentSignature, '.') == NULL) {
    error = allClassLoaderClasses(arrayClassLoader, &classes, &count);
    serror = findComponentClass(env, arrayClassLoader,
                                componentSignature,
                                classes, count, componentClassPtr);
    if (serror != JDWP_ERROR(NONE) || *componentClassPtr != NULL) {
        return serror;
    }
}
// hidden class 或局部未命中：回退 allLoadedClasses()
```

**最有价值的实验、源码与 benchmark 细节：** 在额外加载 70,000 个类的本地 JDI `Object[]` 测量中，单次调用从 17.27 ms 降至 0.156 ms；实算延迟下降 99.10%，约提速 110.7 倍。作者还运行了 191 个 `com/sun/jdi`、1,143 个 `vmTestbase/nsk/jdi`、114 个 `nsk/jdwp` 与 68 个 `nsk/jdb` 测试；总计 1,516 个通过样本，并明确保留既有排除项与不支持 transport 的 skip。该数据仍是单机定向实验，不代表所有调试场景都能达到 110 倍，但复杂应用的全局类数与单 loader 类数差距越大，收益越接近该机制预期。

**适合的工程师背景：** 熟悉 JVMTI/JDWP/JDI、类加载器隔离、hidden class，或正在排查 IDE 调试器在大型服务中元数据查询延迟的工程师。

**预计阅读收益：** 约 30–45 分钟；能掌握如何用语义不变量缩小全局搜索，并理解为什么 hidden class 需要独立 fallback 与专项回归测试。

## 本期结论

两项工作都通过“批量处理或缩小搜索域”消除线性成本：s390 stub 用向量 mask 一次处理多个 oop，但小数组必须正视固定开销；JDI 用 class loader 所有权先把候选集合收窄，再为 hidden class 保留全局兜底。前者说明 GC barrier 向量化需要按数据规模验证，后者说明高倍性能收益往往来自改变搜索空间，而不只是优化循环体。
