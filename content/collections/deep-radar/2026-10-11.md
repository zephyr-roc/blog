## 01 · Rust `Result::unwrap`：把错误值的析构责任移进冷函数，热调用方不再保留 landing pad

**原文与日期：** jnkel，2026-10-10 05:27（中原标准时间）；[Rust PR #164059](https://github.com/rust-lang/rust/pull/164059)、[完整源码 diff](https://github.com/rust-lang/rust/pull/164059/files)、[Compiler Explorer 汇编对照](https://rust.godbolt.org/z/ajjYMTc7Y) 与 [官方 rustc-perf 第一轮结果](https://github.com/rust-lang/rust/pull/164059#issuecomment-6090859813)。

**为什么值得读：** 这是一个只有几行核心 API 变化、却会重画异常控制流的案例。旧实现把 `Err(e)` 以 `&dyn Debug` 借给 `unwrap_failed`；从 Rust 的所有权视角看，`e` 仍属于 `unwrap`。即使 `unwrap_failed` 的正常返回类型是 `!`，在 `panic=unwind` 下它仍可能开始栈展开，调用方必须保留清理路径来析构 `e`。因此几乎永远不走的错误路径，反过来让成功路径也背上栈帧、保存寄存器与 landing pad，并阻碍 MIR inlining。

**核心技术结论：** 补丁把四处 `unwrap_failed(msg, &e)` 改为按值传递，并把冷函数泛型化：

```rust
fn unwrap_failed<T: fmt::Debug>(msg: &str, error: T) -> ! {
    #[inline(never)]
    #[track_caller]
    fn unwrap_failed_inner(msg: &str, error: &dyn fmt::Debug) -> ! {
        panic!("{msg}: {error:?}")
    }
    unwrap_failed_inner(msg, &error)
}
```

移动 `error` 后，析构责任也进入 `unwrap_failed::<T>`；调用方不再需要在 unwind edge 上 drop `e`。真正的格式化仍通过内层 `&dyn Debug` 多态函数完成，避免把整段 formatting 逻辑按错误类型复制。代价是每种 `T` 都要单态化一个很薄的外层冷函数，所以这是“减少调用方 EH/code size”与“增加冷路径 monomorphization”之间的显式交换。

**最有价值的实验、源码与 benchmark 细节：** 作者提供的带析构错误类型汇编把差异直接暴露出来。旧 `unwrap` 入口先 `push r14; push rbx; sub rsp, 24`，即使 `Ok` 路径也要在返回前恢复栈；调用 `unwrap_failed` 后还保留打印、`_Unwind_Resume` 与 `panic_in_cleanup` 的 landing pad。新入口从 `cmp qword ptr [rsi], -1` 开始，`Ok` 分支搬运 24 字节结果后直接 `ret`；只有 `Err` 分支才 `push rax` 并调用 `unwrap_failed::<Error>`。对应 MIR 测试也从一个外部 `Result::unwrap` 调用变成 discriminant switch，成功分支直接移动 payload，证明该函数现在可被 MIR inline。

第一轮官方 rustc-perf 的 instruction count：45 个 primary 样本平均改善 `0.3%`（范围 `-0.6%` 至 `-0.1%`），3 个 primary 样本平均回退 `0.6%`（`0.3%` 至 `1.1%`）；48 个 primary 总体为 `-0.2%`。linked artifact size 的 75 个 primary 结果总体 `-0.3%`，但范围从 `-2.5%` 到 `+1.3%`；bootstrap `487.936 → 487.208 秒`（`-0.15%`）。负向数据不能省略：max-RSS 的两个回退样本为 `+3.8%` 至 `+9.0%`，整体 primary RSS 为 `+0.7%`。这也是 PR 仍带 perf-regression、不能 rollup 的原因。

**适合的工程师背景：** 熟悉 Rust 所有权、panic unwind、MIR/LLVM codegen，或正在优化带异常清理语义的 C++/Rust/Swift 通用库热路径的工程师。

**预计阅读收益：** 约 35–45 分钟；能学会从“按引用还是按值”追到 landing pad、栈帧与内联结果，并掌握如何同时检查指令数、二进制体积与 RSS，避免只凭一段漂亮汇编宣布胜利。

## 02 · rustc `Span::to`：先证明两个 span 都是 inline-context，再把合并压成寄存器运算

**原文与日期：** Josh Triplett，2026-10-08 15:18（中原标准时间）；[Rust PR #163971](https://github.com/rust-lang/rust/pull/163971)、[完整源码 diff](https://github.com/rust-lang/rust/pull/163971/files) 与 [官方 rustc-perf 结果](https://github.com/rust-lang/rust/pull/163971#issuecomment-6056524393)。

**为什么值得读：** 编译器里的 source span 看似只是 `lo/hi/context` 三元组，但宏卫生、父定义与 interning 让一次合并可能需要解码、加锁、递归查询 callsite，甚至把 `SpanData` spill 到栈上。`Span::to` 又是 parser、宏展开与诊断生成的高频路径。这个 PR 的工程价值不只在于“手写 fast path”，而在于先利用前置 span-encoding 改造暴露出的表示不变量：最常见的 `InlineCtxt` 格式已经把 `lo:32 + ctxt:16 + len:15` 装入一个 `u64`，且没有 parent，因此常见情况可以完全绕开 interner 和通用 `SpanData`。

**核心技术结论：** 新实现先尝试把两个参数都解码为 `InlineCtxt`，要求 context 相等，再只用 `lo/len` 计算并集；结果仍能塞回 inline format 就立即返回，否则退到 `#[inline(never)] to_non_inline`：

```rust
if let Some(from) = InlineCtxt::try_from_span(self)
    && let Some(to) = InlineCtxt::try_from_span(end)
    && from.ctxt == to.ctxt
{
    let lo = cmp::min(from.lo, to.lo);
    let len = cmp::max(from.lo + from.len, to.lo + to.len) - lo;
    if let Some(span) = InlineCtxt::try_new_span(lo, len, from.ctxt) {
        return span;
    }
}
self.to_non_inline(end)
```

配套改动同样关键。`Span::new_ordered` 允许已知 `lo <= hi` 的调用点跳过交换检查；`prepare_to_combine` 删除了逻辑上不可能改变结论的 `source_callsite()` 递归；`try_metavars` 只传两个 context，并以 `Option<SpanData>` 返回真正需要替换的一侧，避免先把两份完整 `SpanData` 落栈。它们共同把“常见格式、相同 context、无 parent、结果仍可内联”的条件收窄成一个可由寄存器完成的路径，而不是把所有罕见语义塞进热函数。

**最有价值的实验、源码与 benchmark 细节：** 作者明确指出最终 `Span::to` 热路径没有栈帧，也不保存寄存器；此前 profile 中可见的 `SpanData` spill 被拆分参数和返回值消除。官方 rustc-perf 给出罕见的整齐 primary 结果：138 个 instruction-count primary 样本全部改善，均值 `-0.5%`，范围 `-1.2%` 至 `-0.3%`，没有 primary 回退；79 个 secondary 改善样本均值 `-0.8%`，另有 6 个 secondary 回退 `0.6%`–`0.7%`。bootstrap `492.261 → 488.235 秒`，缩短 `4.026 秒`（`-0.82%`）；artifact size `408.66 → 406.28 MiB`（`-0.58%`）。

仍需保留噪声边界：cycles 的 161 个 primary 显著样本总体只有 `-0.2%`，范围 `-6.3%` 到 `+5.0%`；max-RSS 的 80 个 primary 显著样本总体 `-0.4%`，但单项范围 `-2.8%` 到 `+2.2%`。因此最稳的结论是“动态指令普遍减少”，而不是所有 wall-clock 或内存样本都等比例改善。PR 还建立在 span compression overhaul 之上，评审和复测都应锁定同一基线。

**适合的工程师背景：** 熟悉 rustc span/hygiene、紧凑数据表示、profile-guided hot-path 分拆，或在编译器中优化高频小对象与 interner 的工程师。

**预计阅读收益：** 约 45–60 分钟；能掌握如何把表示层统计转成 fast-path guard、如何把罕见语义隔离到冷函数，以及怎样用全量 benchmark 分布验证微优化没有只照顾单个 workload。

## 本期结论

两篇材料展示了同一种优化方法在不同层次的应用：先把罕见语义移出热路径，再让常见路径只携带完成工作所必需的状态。`Result::unwrap` 通过移动所有权把析构和 unwind 清理责任交给冷函数，换来成功路径无 landing pad；`Span::to` 则用紧凑表示的不变量把通用 interner/hygiene 逻辑隔离到 `to_non_inline`，让最常见合并留在寄存器中。真正可迁移的经验是同时验证控制流、汇编和全量 benchmark 分布，并把回退样本留在结论里。
