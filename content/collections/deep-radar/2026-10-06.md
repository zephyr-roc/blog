## 01 · HotSpot：Float16 重排不做浮点运算，因此可以直接借用 short permute

**原文与日期：** Jatin Bhateja，2026-10-05 12:53（中原标准时间）；[OpenJDK PR #33198](https://github.com/openjdk/jdk/pull/33198)、[完整源码 patch](https://github.com/openjdk/jdk/pull/33198/files) 与 [JDK-8389741](https://bugs.openjdk.org/browse/JDK-8389741)。

**为什么值得读：** `Float16Vector` 的算术需要半精度语义，但 `rearrange` 只搬运 lane，从不解释 binary16 的指数和尾数。旧实现仍因 `T_FLOAT16` 不在普通 lane 类型白名单而回退到 Java 代码。这个补丁最有价值的地方不是新增一套 FP16 shuffle，而是识别出“语义类型”和“物理 lane 宽度”可以在这一步分离：把 Float16 映射成同宽的 `T_SHORT`，即可复用已有 16-bit permute 后端。

**核心技术结论：** `LibraryCallKit::inline_vector_rearrange` 原先先调用 `is_supported_lane_type(vltype)`，导致 Float16 在进入通用 `VectorRearrange` IR 之前就被拒绝。patch 删除这层过早检查；后续类型解析已经会把 `T_FLOAT16` 映射到 `T_SHORT`，因此 masked 与 unmasked rearrange 都能生成 16-bit lane permutation，而不会改变任何 bit。

```cpp
// rearrange 只置换 lane；T_FLOAT16 在后续被解析为同宽的 T_SHORT。
if (!arch_supports_vector(Op_VectorRearrange, num_elem, elem_bt, ...)) {
    return false;
}
```

这里的工程方法很可迁移：intrinsic 入口不应重复维护一份比后端更窄的类型能力表，否则新的表示类型即使物理操作完全兼容，也会在前门被挡回慢路径。

**最有价值的实验、源码与 benchmark 细节：** 作者在支持 AVX-512 FP16 的目标机上测试 `Float16Vector.rearrange`。`vectorDim=1024` 从 `217.410` 提升到 `21,842.915 ops/ms`，约 100.47 倍；`vectorDim=2057` 从 `93.602` 提升到 `4,047.767 ops/ms`，约 43.24 倍。这里的大数量级不是“一条 shuffle 快 100 倍”，而是从整段 Java fallback 切回编译器 vector IR 的路径差异；2057 不是整齐倍数，尾部处理也解释了它为何低于 1024 的相对收益。

新增 IR 测试覆盖 64、128、256、512-bit species，以及 masked / unmasked 两条路径，并断言生成 `VectorRearrange`。输入包含 identity、reverse 和交替 mask，结果通过 Float16 与 raw short bits 的往返比较，验证搬运后 bit pattern 未改变。较小宽度要求 AVX512BW+VL，512-bit 路径要求 AVX512BW；这让“源码允许 intrinsic”与“目标后端确有对应指令能力”分开验证。

证据边界不可省略：JMH 每组只有 `Cnt=2`，没有误差区间；作者只给出一台目标机，也没有发布最终反汇编。100.47 倍和 43.24 倍足以证明 fallback 是数量级瓶颈，但不足以外推到所有 x86、AArch64 或任意 vector species。

**适合的工程师背景：** 熟悉 HotSpot C2、Vector API、IR framework 或 SIMD lowering，想理解新数值类型如何复用现有整数后端的 JVM 工程师。

**预计阅读收益：** 约 30–45 分钟；能学到 intrinsic 入口的 capability 边界、表示类型复用、IR 测试矩阵，以及如何从数量级 benchmark 反推慢路径是否真正被消除。

## 02 · Rust：给 fold specialization 打开内联窗口，才有机会消掉 adapter 栈

**原文与日期：** lcnr，2026-10-05 09:58（中原标准时间）；[Rust PR #163775](https://github.com/rust-lang/rust/pull/163775)、[完整源码 patch](https://github.com/rust-lang/rust/pull/163775/files) 与 [rustc-perf 指令数对比](https://perf.rust-lang.org/compare.html?start=260f1acad9d7f70b5b56a636a9dc5a7f76150417&end=ddc0f5fe3d05348f68f2f635684aec7bf6ce6a48&stat=instructions:u)。

**为什么值得读：** Rust iterator 的“零成本”不是语法天然保证，而依赖 adapter 的 specialization hook、monomorphization 和 LLVM 能同时看到控制流。`Chain`、`Map` 已实现专用 `fold` / `try_fold`，但四个方法缺少 `#[inline]`；跨 crate 边界时，优化器可能只能看到调用，不能把 closure 与两段 iterator 的状态机融合起来。这个 PR 只有四行注解，却把一个抽象成本问题定位到非常具体的可见性边界。

**核心技术结论：** patch 分别给 `Chain::try_fold`、`Chain::fold`、`Map::try_fold`、`Map::fold` 加 `#[inline]`。`fold` 和 `try_fold` 是 iterator adapter 避免逐项 `next()` 调度的关键入口；当实现体随 metadata 暴露给调用方后，LLVM 才能继续内联映射 closure、传播 accumulator，并消掉 `Chain` 在前后 iterator 之间切换的分支与中间调用。

```rust
#[inline]
fn fold<Acc, Fold>(self, init: Acc, fold: Fold) -> Acc
where
    Fold: FnMut(Acc, Self::Item) -> Acc,
{
    // 现有实现不变；变化只是允许调用方跨边界继续优化。
}
```

这也说明 `#[inline]` 的真实含义不是强制复制代码，而是让下游优化器获得候选实现体。收益来自“解锁后续简化”，因此必须用真实调用图验证，不能只看 patch 行数。

**最有价值的实验、源码与 benchmark 细节：** rustc-perf 的 17 个 primary 样本中，15 个指令数改善，均值 -1.8%、范围 -13.3% 至 -0.2%；2 个回退，均值 +1.0%、范围 +0.6% 至 +1.5%。把全部 primary 合并后平均为 -1.5%。secondary 有 36 个改善，平均 -0.5%、最大 -3.2%。这组分布比单个“最高 -13.3%”更有价值：内联确实让多个真实编译 workload 的 adapter 栈被简化，但收益集中度很高，并非整齐普降。

二进制体积的 primary 汇总平均 -0.9%，30 个样本改善约 -1.0%，但仍有一个样本 +3.4%；primary RSS 也出现一个 +1.2% 回退。cycles 的 primary 5 个改善平均 -5.7%，secondary 却有 9 个回退平均 +4.4%，说明低层计数和 wall-clock 仍受噪声影响。bootstrap `490.682 → 490.616 s`，仅约 -0.01%，基本持平。评审者据此认可存在“相当可观的收益”，但这些负向尾部仍意味着后续需要关注编译时间、代码布局与单 crate 膨胀。

最值得迁移的验证方式是同时看 instructions、cycles、RSS、binary size 和 bootstrap：内联优化若只降低某个热点的动态指令，却抬高优化器内存或某些产物体积，工程决策就不能只报最好一列。

**适合的工程师背景：** 熟悉 Rust iterator、monomorphization、LLVM 或 rustc-perf，想理解“零成本抽象”何时会因跨 crate 内联边界失效的编译器与库工程师。

**预计阅读收益：** 约 25–40 分钟；能掌握 `fold` specialization 在 adapter fusion 中的位置、`#[inline]` 的跨 crate 语义，以及如何用多指标分布判断小 patch 的真实代价。

## 本期结论

两篇材料都说明抽象能否“零成本”，取决于优化器是否在正确层级看到足够信息。HotSpot 让 Float16 的纯 lane 置换复用 short permute，直接消除 Java fallback，两个样本分别提升约 100.47 倍和 43.24 倍；Rust 仅补四个内联注解，就让 17 个 primary 样本指令数平均下降 1.5%，但个别指令、RSS 与体积指标仍回退。可迁移的方法是先分离语义类型与物理表示，再检查跨模块可见性，最后用完整分布而非最佳样本决定是否接受优化。
